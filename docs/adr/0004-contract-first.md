# ADR-0004：契约优先（Contract-First）

| 项目 | 内容 |
| --- | --- |
| 状态 | 已接受（Accepted） |
| 日期 | 2026-11-04 |
| 决策者 | 架构组 |
| 关联 | 《接口契约》全文 / §16；《实施架构》§1 / §2；《开发指南》§4 |

## 背景

前后端由不同成员并行开发，且脚手架阶段目标之一是**锁定 29 命令 / 14 事件 / 配置 Schema v3**
的边界，让 UI、Rust 骨架、mock 后端与 CI 同时推进。若先写实现再「顺带」对齐接口，常见问题：

- 前端假设的字段名/大小写与 Rust serde 序列化不一致（`camelCase` vs `snake_case`）；
- 事件时序（`task.started` 必须先于首个 `task.delta`）无人定义，联调时反复排查；
- 错误码与降级链散落，前端无法统一 toast/fallback；
- mock 行为与真实后端漂移，浏览器联调通过但桌面版失败。

## 决策

1. **`docs/接口契约.md` 是唯一事实来源**：命令、事件、类型、配置、错误码、骨架模式行为、
   主题 token 全部写在该文件，且为不可绕过的评审对象。
2. **双端同构**：`src/shared/contract/`（TS 类型、`COMMANDS`/`EVENTS` 常量）与
   `src-tauri/src/contract/`（Rust 结构、serde 约定）逐字段对应契约；命令名/参数名逐字一致。
3. **版本化**：`IPC_CONTRACT_VERSION`（当前 `1`）随破坏性变更递增，出现在 `Stats.contractVersion`；
   契约文末「修订记录」必须更新。
4. **变更流程固定**（见《开发指南》§4）：先改契约 → 同步双端 contract → （必要时）递增版本 →
   同步 mock → 更新 CHANGELOG → 跑 `typecheck` / `scripts/verify.ps1`。
5. **mock 是契约的第二个实现**：`src/shared/ipc/mock.ts` 必须按契约 §12 的确定性行为实现，
   使「无 Rust 环境」也能验收同一套交互。
6. **新增只增不改**：新增可选字段前端容忍未知字段、Rust 加 `#[serde(default)]`；删除需两个版本
   弃用期。

## 理由与备选

- **并行开发**：契约先冻结后，前端可用 mock 完整开发，Rust 可独立实现，最后在真实 IPC 上对接。
- **可评审**：接口形状在代码之前被评审，减少返工；错误码/事件时序等「隐性约定」显式化。
- **可测试**：Rust 侧对 contract 结构做序列化测试；TS 侧 `typecheck` 保证字段引用有效。
- **备选 1：从 Rust 自动生成 TS**（`ts-rs`/`schemars`）——能消除手写漂移，但生成物可读性差、
  文档仍需单独维护，且脚手架阶段需要「可读的契约文档」作为协作锚点；保留为后续增强方向。
- **备选 2：OpenAPI / gRPC**——对本地 IPC 过重，增加生成链路与依赖，收益不明显。
- **备选 3：各写各的、联调时对齐**——历史经验证明会反复漂移，正是本 ADR 要解决的问题。

## 后果

- **三处维护**（文档、TS、Rust）：变更成本上升，需靠流程与评审保证一致性；这是有意的取舍。
- 契约文档较长（§1–§16），新增成员需先读；已在 README/开发指南给出阅读顺序。
- 前端不能「临时」调用未入契约的命令；任何新能力都必须走命令表，避免后门。
- mock 与真实实现的行为差异成为一类专门缺陷，需要以契约 §12 为基准测试。
- 版本递增需要同步检查 `Stats.contractVersion`、前端展示与发布说明。
