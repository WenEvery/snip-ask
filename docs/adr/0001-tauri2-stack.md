# ADR-0001：桌面框架选择 Tauri 2 + Rust + React / TypeScript

## 背景

产品定位是「轻量快速、托盘常驻」的 Windows 截图问答工具，硬性目标是**主安装包 ≤ 25MB、
冷启动 ≤ 1.5s、空闲内存 ≤ 120MB**，并且需要 Win32 级别的截图与全局热键能力。
同时团队希望保留跨平台（macOS/Linux）的演进空间，并复用 Web 技术做复杂 UI（冻结层、选框、
流式 Markdown、设置页、引导向导）。

候选框架的差异主要在「运行时体积 / 内存」与「系统能力可达性」：

| 方案 | 体积 / 内存 | 系统能力 | UI 生态 |
| --- | --- | --- | --- |
| Electron | 运行包 80–150MB，空闲内存 150–300MB | Node 原生模块可做 | 最成熟 |
| WPF / WinUI 3 | 小 | 最直接（C#/WinRT） | XAML，Web 复用差 |
| Flutter desktop | 中 | 需 FFI | 自绘，文本/输入法细节成本高 |
| **Tauri 2** | **最小（系统 WebView2）** | **Rust FFI 直接调 Win32** | **React/TS 成熟** |

## 决策

采用 **Tauri 2**：Rust 2021 后端（`tauri` 2.x + tokio）承担全部系统能力与网络访问，
前端使用 **React 18 + TypeScript 5 + Vite**，运行在系统 WebView2 中；本地推理引擎后续以
sidecar 子进程接入。Rust 侧按 `commands → services → domain`、`platform` 隔离 Win32 的分层组织。

## 理由与备选

- **体积与内存**：Tauri 复用系统 WebView2，安装包与常驻内存显著优于 Electron，是满足
  「≤25MB / ≤120MB」目标的现实路径（报告 §3.3 加权评分中 Tauri 最优）。
- **系统能力**：截图（BitBlt/WGC）、全局热键、Credential Manager、托盘、单实例都需要原生 API；
  Rust 通过 `windows` crate 可直接调用，且可将 `unsafe` 收敛到 `platform/` 一个目录。
- **安全边界**：前端不接触网络与密钥（见 ADR-0002），Rust 侧统一做超时、重试、脱敏与计费。
- **UI 生产力**：冻结层、选框、放大镜、菜单、流式结果、设置页与引导都是 Web 强项，React 生态成熟。
- **跨平台潜力**：Tauri 支持 macOS/Linux，未来仅需替换 `platform/` 实现。
- **备选 Electron**：开发最快，但体积/内存与「轻量」定位冲突；**备选 WPF**：原生但 UI 复用与
  跨平台潜力差、团队 Web 技术栈无法复用；**备选 Flutter**：自绘引擎在中文输入法、文本选择、
  系统 WebView 集成上细节成本高。

## 后果

- 开发环境需要 **Rust + MSVC 链接器 + Windows SDK**，比纯前端项目门槛高；无 Rust 时可用
  `pnpm dev:web` 的 mock 后端开发 UI（见 ADR-0005）。
- 依赖系统 **WebView2 Runtime**（Win11 自带，Win10 需安装/引导），版本差异需在兼容性测试中覆盖。
- 单个应用进程 + 后续本地推理 sidecar；进程管理与端口分配需要 `platform::process` 统一封装。
- 前端与后端分属两套语言，契约同步成本上升，因此采用**契约优先**（ADR-0004）双端同构约束。
