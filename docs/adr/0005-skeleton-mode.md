# ADR-0005：骨架模式（Skeleton Mode）

| --- | --- |
| 状态 | 已接受（Accepted） |
| 日期 | 2026-11-04 |
| 决策者 | 架构组 |
| 关联 | 《接口契约》§1.8 / §12；《实施架构》§1 / §9；《可行性研究报告》§3.4 |

## 背景

脚手架阶段的目标是「跑通空壳闭环」：热键 → 冻结 → 框选 → 菜单 → 流式结果。但真实能力
（Win32 捕获、RapidOCR、HTTP 网关、本地 LLM）依赖工具链、API Key、网络与 1–8GB 模型，
且部分能力在本机不可用（无 Rust/MSVC、无密钥、无 GPU）。如果必须等真实能力就绪才能联调 UI，
前后端将无法并行，验收也缺少确定性。

此外，演示与手动验收需要**每次结果一致**的行为：真实 OCR/LLM 的输出受截图、模型、网络影响，
不适合作为 UI 流程的回归基线。

## 决策

引入 **骨架模式（skeleton mode）**，默认开启（`advanced.skeletonMode = true`）：

1. **能力占位**：捕获 / OCR / LLM / 搜索 / 翻译 / 模型下载 / 更新 / 凭据等外部能力均提供
   `Skeleton*` 变体，与真实实现**同一 trait**，由 `AppState.settings.skeleton_mode` 分支选择。
2. **行为确定性**：严格按契约 §12 固定时序与输出（例如 OCR 150ms→`scanning`、400ms→`done`；
   流式块 25–40ms；翻译输出 `【骨架模式译文】` + 原文；下载每 100ms 前进 4%）。
3. **事件流一致**：骨架模式发出与真实实现完全相同的 `overlay:ready` / `ocr:status` /
   `task:started` / `task:delta` / `task:done` 等事件（`engine = "skeleton"`、`usage` 为固定值），
   前端不得依赖真实网络或非确定性时序。
4. **不伪造真实能力**：骨架模式不访问真实 Credential Manager（内存 map 模拟）、不联网、
   不启动本地引擎；`open_external` 仅打印日志。
5. **可关闭**：关闭后进入真实路径；尚未实现的分支返回 `SA-9001 SkeletonNotImplemented`，
   并通过 `// TODO(real): ...` 标注接入点，保持调用方签名不变。

## 理由与备选

- **并行开发**：前端在纯浏览器（mock 后端）+ 桌面骨架模式两处都能走完整 UI 流程；Rust 骨架可独立编译与单测，不必等待真实能力。
- **可验收**：确定性输出让「框选 → 菜单 → 流式结果」成为可回归的手动/自动验收基线，也是无密钥、无网络环境下的演示路径。
- **降低门槛**：开发机无 Rust/MSVC、无 API Key 时仍能推进（报告 §3.4「Rust 门槛」的应对）。
- **风险隔离**：真实实现接入时只需替换 service 内部，不需要改动命令与事件契约。
- **备选 1：仅前端 mock**——无法验证 Rust 命令/事件/状态机，契约漂移风险高，且桌面版无法演示。
- **备选 2：逐能力 feature flag**——组合爆炸，验收矩阵难维护；统一开关更简单。
- **备选 3：空实现（返回空/立即完成）**——UI 无法验证流式、错误、状态机分支，放弃。

## 后果

- 存在「骨架逻辑混入真实路径」的风险：每个 `Skeleton*` 必须与真实实现隔离在同一 service 的
  分支中，接入真实能力时删除分支或改为默认真实 + 骨架回退；评审重点检查。
- 骨架时序是人为设定的（如 OCR 400ms），不能当作性能依据；真实性能以 spike S-02/S-03 为准。
- 契约 §12 是 skeleton 行为的规范源，前端若依赖 skeleton 特有输出（如固定文本）需容忍真实输出。
- 下载占位会写 `models/<id>/.installed`（空文件），需在真实下载器接入时清理该状态。
- 安全侧：骨架模式不读写真实凭据，避免开发期误存密钥；关闭骨架后必须走 Credential Manager。
