# ADR-0002：前端不接触网络与密钥，能力全部后置到 Rust

## 背景

工具需要调用用户的 AI 服务（BYOK）：LLM、搜索、翻译。密钥若出现在 WebView 中，会暴露在
JS 运行时、DOM、内存快照、`localStorage`、前端日志与崩溃转储里，任何前端依赖被投毒或 XSS
都可能导致密钥泄露。与此同时，云端调用需要统一处理超时、重试（429/5xx）、费用计量、
日志脱敏与上传开关——这些逻辑若散落在多个前端窗口，行为必然不一致。

Tauri 的 IPC 边界提供了一个天然的「唯一能力出口」：WebView 只能 `invoke` 命令、`listen` 事件。

## 决策

1. **前端只做表现层**：`src/` 不直接使用 `fetch`/`XMLHttpRequest`/第三方网络 SDK，
   不读写密钥，不写配置文件；所有外部能力经 `src/shared/ipc` 的 `ipc.invoke(command)` 调用。
2. **密钥只在 Rust 侧**：`CredentialService` 是唯一访问 Windows 凭据管理器的入口，
   请求前取用、用完即弃；`ConfigView` 只返回 `hasKey` 与 `keyMask`（`••••` + 后四位），
   任何命令入参/出参/事件载荷都不得出现明文 Key。
3. **跨窗口状态来自后端**：业务数据不落 `localStorage`（mock 模式除外），窗口间通过事件
   或命令返回值同步（如 `config:changed`、`task:delta`）。
4. **统一出口**：超时、重试、错误码映射（`SA-30xx`/`SA-40xx`）、用量计量、日志脱敏集中在
   Rust 网关层，前端只消费 `AppError` 与 `fallback` 列表。
5. **强约束**：契约 §1.7 与 §11 写死该边界；评审与静态检查（前端代码不得出现 `apiKey` 字样
   的传输）共同保证。

## 理由与备选

- **攻击面**：WebView 渲染的是用户内容（截图上的文字、模型输出），是潜在注入面；把密钥与网络
  放在 Rust 侧后，即使前端被注入也无法直接读取凭据。
- **一致性**：所有供应商共用一套重试/退避、超时、计费与脱敏逻辑，避免每个窗口各写一份。
- **可测试性**：网关可注入 fake 引擎单测降级链；前端可用 mock 后端（§12）完整联调。
- **备选 1：前端直连**——实现最简单，但密钥进 JS 内存/`localStorage`、CORS 与多窗口重复逻辑，
  且无法统一计费与脱敏，放弃。
- **备选 2：本地 helper 进程 + 前端 HTTP**——多一个进程与端口面，仍需前端持有临时凭据，收益低。
- **备选 3：加密后放前端**——密钥最终仍需在 JS 中解密，等同未加密，放弃。

## 后果

- 新增任何外部能力都必须先加**命令/事件**（契约成本，见 ADR-0004），不能前端随手 `fetch`。
- 浏览器 `pnpm dev:web` 依赖 mock 后端实现同样的契约行为，mock 行为偏差会误导联调，
  因此 mock 必须按契约 §12 维护。
- 调试后端问题需看 Rust 日志（`RUST_LOG`）而非浏览器网络面板；这是可接受的开发成本。
- 后续若引入本地 sidecar（llama.cpp），端口与生命周期也只由 `platform::process` 管理，
  前端不感知进程细节。
