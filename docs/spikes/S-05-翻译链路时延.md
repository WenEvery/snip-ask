**测量纪律**：正式时延测量前用 `.verify/bench.lock` 独占（`owner=ext-bench`，由长驻 holder 进程持锁），

## 2 被测口径

- **样例**：200 字中文产品文案（160 个汉字 + 40 个标点/空格/ASCII 标识符，共 200 字符）。
  与 `bench_translate.py`、`bench_local_translate.mjs` 中 `SAMPLE_TEXT` 逐字一致，两边脚本均断言长度 = 200。
- **提示词**：`resources/prompts/translate.md`（版本 1）正文，按 `prompt_engine` 语义渲染
  `{sourceLang}=zh-CHS`、`{targetLang}=en`、`{glossary}=""`；渲染后 762 字符、prompt_tokens = 458。
- **采样参数**：`temperature=0.2`（产品 `config.providers[].temperature` 默认值）、`top_p=0.95`、
  `top_k=0`、`repeat_penalty=1.0`、`max_tokens=1024`（产品默认值）。
- **判定阈值**（`docs/技术验证清单.md` §2）：云端 200 字 **≤1.5s**；本地 1.8B Q4 **≤8s**（首次加载另计）。
  统一以**端到端非流式总耗时 P95** 对比阈值。

`dashscope_empty_key_body.json`。结论：**本机没有任何云端 Key，云端时延无法做真实测量 → BLOCKED**。

### 3.2 基准脚本（填 Key 即可一键复跑）

`scripts/spikes/s05_s06/bench_translate.py`：OpenAI 兼容 `/chat/completions`，从环境变量读
`SNIPASK_BENCH_BASE_URL` / `SNIPASK_BENCH_MODEL` / `SNIPASK_BENCH_API_KEY`，跑 warmup + 20 次实测，
记录 HTTP 状态、首字节（响应头到达）、总耗时、`usage` token 用量、失败率，输出 P50/P95/max 与 JSON；
支持 `--stream`（额外记录首 token 延时）与 `SNIPASK_BENCH_EXTRA_JSON`（如 Qwen-MT 的 `translation_options`）。
无 Key 时打印 BLOCKED 与解锁步骤并以**退出码 2** 结束；`--self-test` 用内置 mock 服务验证框架。

### 3.3 框架自检（MOCK，不作为验收依据）

`--self-test --runs 5 --warmup 1`：6 次请求全部 HTTP 200，总耗时 P50 71.4ms / P95 71.6ms（mock 服务固定
~70ms 延时 + 回环网络），首字节 P50 71.2ms；输出 `meta.mode="MOCK_SELF_TEST"`、判定 `MOCK_SELF_CHECK_OK`。
**该数字只证明测量框架可跑通，不代表任何云端供应商的真实时延。**

### 3.4 解锁步骤（拿到 Key 后 1 条命令）

```powershell
$env:SNIPASK_BENCH_BASE_URL = "https://api.deepseek.com/v1"      # 或 DashScope 兼容模式
$env:SNIPASK_BENCH_MODEL    = "deepseek-chat"                    # 或 qwen-mt-turbo / qwen-mt-lite
$env:SNIPASK_BENCH_API_KEY  = "<你的 Key>"
python scripts/spikes/s05_s06/bench_translate.py --runs 20 --warmup 2
```

预期与风险：DeepSeek `deepseek-chat` 200 字非流式通常 1–2s；Qwen-MT 专用翻译模型可能在 0.5–1.5s 区间，
但均需真实测量确认。若 P95 接近 1.5s，建议对比 `--stream` 首 token 延时与 max_tokens 限制。

### 4.2 方法

1. 启动 `llama-server.exe -m HY-MT1.5-1.8B-Q4_K_M.gguf -c 4096 -t 16 --port 39281 --host 127.0.0.1 --no-webui`（`-ngl 0`）。
2. 轮询 `GET /health` 至 200，记录「进程启动 → 就绪」冷加载耗时（首次加载另计）。
3. warmup 2 次后正式 10 次（原计划 20 次；本轮受并行负载与档期影响降为 10 次，均值/P95 的波动已在 §4.3 交叉验证），
   `POST /v1/chat/completions`，消息体为渲染后的 200 字翻译提示词；记录客户端总耗时/首字节与 llama.cpp 服务端
   `timings.prompt_ms`（prefill）、`timings.predicted_ms`（decode）、`predicted_per_second`（tok/s）、`usage`。
4. 通过 PowerShell `Get-Process` 记录 llama-server 的 `WorkingSet64/PrivateMemorySize64/PeakWorkingSet64`。
5. 线程调优：`-t 6` 与 `-t 16` 各 2 次，选 mean 更低者；正式数据用 `-t 16`。
6. 输出长度敏感性：`max_tokens=100` 实测 2 次，与 150 token 完整译文对比，验证 decode 时长与 token 数近似线性。

### 4.4 结果与阈值对比

| 项 | 阈值 | 实测 | 判定 |
| --- | --- | --- | --- |
| 云端 200 字 ≤1.5s | 1,500 ms | 无 Key，未测 | **BLOCKED**（非 FAILED，不能编造） |
| 本地 200 字 ≤8s（首次加载另计） | 8,000 ms | P50 11,759.50 ms / P95 21,836.86 ms / min 9,886.40 ms | **FAILED** |
| 本地冷加载 | 另计 | 1.46–2.88 s | 记录 |
| 本地常驻内存 | —（S-13 输入） | WorkingSet 2.05–2.10 GiB，Private 1.11 GiB | 记录 |

**未达标原因分解**：单次 ≈ prefill 2.6–3.9s（458-token 产品提示词）+ decode 7.3–19.9s（150 token，
CPU 生成速率 7.5–20.5 tok/s，受并行负载影响）。瓶颈是 **CPU decode 速率 + 完整 150-token 输出长度**，
不是网络或脚本开销；prefill 也因产品提示词较长而不可忽略。

## 5 处置（可行动项）

1. **产品策略（最高优先）**：本地翻译定位为「可用但较慢」，默认云端；本地路径必须流式展示首字
   （prefill+首 token 约 2.5–3.5s 可感知），并在结果窗口标注后端与预计时长；受限模式（无 Key）下保留本地翻译
   （S-07 输入：本机 2.10 GiB 常驻，16GB 机器可承受）。
2. **阈值修订或硬件门槛**：把清单「本地 ≤8s」改为分级指标，例如「独显/Apple Silicon ≤2s；纯 CPU 16 线程
   P50 ≤12s」；否则该指标在 i5/16GB 级纯 CPU 上不成立。当前建议清单备注中直接引用本报告数据。
3. **GPU offload（需排期实测）**：RTX 4060 Laptop 8GB 可容纳 1.1GB Q4 模型，`-ngl 99` 预期 decode 100+ tok/s，
   总耗时有望 <2s；需实现「探测 GPU → 自动 ngl → 失败回退 CPU」并在文档注明（i5+核显用户仍走 CPU 慢路径）。
4. **更小/专用模型**：`resources/models.manifest.json` 已有 `opus-mt-zh-en`（300MB CTranslate2 中英专用），
   预期亚秒级，建议作为本地翻译默认候选做后续 spike（本次不在范围）。
5. **提示词瘦身 + prefix cache**：458-token 提示词的 prefill 约 2–4s；若产品实际开启 llama.cpp prefix cache，
   prefill 可显著降低；同时可把提示词压缩 30%–50%。但这只能解决 prefill，完整译文 decode 仍 >8s。
6. **限制输出/流式**：`max_tokens≈120` 可把 P95 压到 7s 左右，但译文截断不可接受；替代方案是流式输出 +
   分段翻译（长文本按段并发），把「完整译文到齐」压力转化为可接受的渐进体验。
7. **云端兜底**：拿到 Key 后按 §3.4 复跑云端；云端 200 字预期 1–2s，可与本地形成「云端优先、本地离线兜底」。
8. **S-13 资源降档输入**：本机 1.8B Q4 常驻 WorkingSet ≈2.1 GiB（Private 1.11 GiB），16GB RAM 机器可用；
   但在 8GB RAM 机器需降档/禁止常驻，`idleUnloadSec=600` 需要在应用层实现（llama-server 无此能力）。
