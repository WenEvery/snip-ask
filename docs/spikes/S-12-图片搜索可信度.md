### 2.2 真实四段流水线

与 S-06 真实链路口径一致，按 `resources/prompts/image_search.md`（版本 1）拆两阶段：

1. **① 视觉识别**：图片 base64（data URL）+ 阶段 A 提示词 → 输出「识别结果」+「检索词」；
2. **② 检索词**：本地解析阶段 A（quick 1 组）。**可编辑性属产品 UI 能力，本基准只评生成质量**；
3. **③ 检索**：`POST /v1/tools/search`（count=5，真实联网，非 mock）；
4. **④ 摘要**：把识别结果 + 真实检索结果（标题/URL/snippet）交同一模型 → 输出「结论」+「来源」。

请求参数：`temperature=0`、`thinking={"type":"disabled"}`；视觉 `max_tokens=900`、摘要 `max_tokens=900`。
**实际执行 30 张、60 次 chat 调用 + 30 次 Search，0 失败**（`client_stats`）。
逐图端到端耗时（含两阶段模型 + Search）P50 **5.13s**、max 7.15s（本项不设时延阈值，仅记录）。

### 3.3 来源真实性

- **疑似编造 1 条**：`product-01-headphones`。模型把 Search 返回的 hktvmall 商品链接改写成了另一个门店/商品的路径
  （`/hktvmall/zh_CN/main/EG-Shop/s/H9626001/…` vs 检索结果 `/hktvmall/zh/main/Day-Day-Shop/s/B0031001/…`），
  URL 身份不一致且页面 404。属于「模型改写 URL」而非纯空想，但对外展示即为**不可访问的错误来源**。
- **疑似截断 2 条**：模型输出长 URL 时被自身截断（末尾 `%`、`-`），如 `product-04-coffee` 的 Amazon 链接截断在
  `content-id=amzn1.sym.07d291d6-18c2-`。截断 URL 仍可通过原路径访问，但作为来源不可靠。
- 其余 135 条引用 URL 均可在本次 Search 结果中按 URL 身份找到对应项（其中另有 2 条存在截断风险，见下）。

> **测量口径修正说明**：首轮统计用「保留 query 的 URL 归一化」，把 `amazon.co.jp/dp/B0DJNFGQCG/ref=sr_1_12?…`
> 与去掉追踪参数的同一页面误判为「编造」（4 条）；修正为 `scheme://host/path` 身份比对并单独统计截断后，
> 编造降到 1 条。修正过程与原始 JSON 均保留（`*_rescored.json`），可复算。

### 3.4 不确定标注

- 4 张 `expect_uncertain` 图（低对比度小字、小字号热力图、虚构产品、压缩混淆 JS）**4/4 全部显式标注**。
- 另 26 张非标记图也**全部**出现了不确定表述（26/26），说明阶段 B 提示词「不确定处直接标注」被稳定执行；
  代价是**过度 hedging**：如 `chart-08-stacked` 因图中无坐标轴刻度而反复声明「数值不确定」。
- 典型正面样例（虚构产品，`product-07-fictional`）：
  > 「页面显示『评分 无 · 已售 2.3 万+』，该销量与『未上市、仅内部评审』的样机描述存在矛盾，不确定其真实性或统计口径。
  > 检索结果中未出现『Nebula X9 智能音箱』这一产品……故无法佐证该音箱的存在、参数或价格，相关产品信息不确定。」

  —— 模型**没有编造参数/价格**，并主动指出图文矛盾，符合 S-12 的防幻觉目标。

### 4.4 检索词相关性偏弱（3 例，自动判定未命中、执行者复核通过）

| 图 | 生成检索词 | 期望词 | 执行者判断 |
| --- | --- | --- | --- |
| text-05-table | `本地模型对比` | Qwen2.5 / HY-MT1.5 / P95 时延 | 相关（上位词），但**泛化过度**：检索到的是通用模型对比，未用图中表内具体模型名 |
| chart-08-stacked | `堆叠柱状图` | 请求构成 / 云端 / 浏览器 | 相关（图表类型），**过泛**：未带业务关键词，检索结果与图中数据无关 |
| code-07-minified | `bundle.min.js` | minified / JavaScript / webpack | 相关（文件名），**过窄**：未结合识别到的 UMD/`snipask` 特征 |

**判断**：3 例检索词都「与图像内容相关」，因此执行者复核算 30/30；但暴露了 quick 模式只生成 1 组检索词的弱点——
当画面信息量大（表格/图例/代码）时，模型倾向选最概括的词，导致检索结果泛化。这与 S-06 结论一致（quick 1 组；
deep 2–3 组更稳）。

### 4.5 四段与来源格式

- 30/30 均输出四段；「来源」行均为「标题 - URL」格式，URL 数 1–5 条/图（平均 4.5，共 136 条；2 图返回 3 条、
  1 图返回 1 条、1 图 2 条）。
- 未出现「未检索到可靠来源」的图（Search 均返回结果）；产品在 Search 空结果时的兜底文案由提示词约束覆盖，
  本轮未触发。

## 5 结论与阈值对比

| 阈值 | 要求 | 实测 | 判定 |
| --- | --- | --- | --- |
| 四段齐全 | 100% | **100%**（30/30） | **DONE** |
| 来源可访问率 | ≥95% | raw **59.6%**；乐观上界 **94.1%** | **FAILED** |
| 不确定处显式标注 | 100% | **100%**（4/4） | **DONE** |

**S-12 结论：FAILED（来源维度）**。四段结构与不确定性标注两项已达标；来源可访问率与来源真实性不达标，
且失败原因可分解为「Search 结果本身含约 5.9% 死链」+「反爬/本机网络限制放大脚本口径失败」。

## 6 处置建议（给产品实现）

1. **来源 URL 预校验（最高优先）**：展示前对每条来源做 HEAD/GET 快速校验（≤2–3s、失败不重试），
   2xx/3xx 才作为「来源」显示；404/超时降级为「未验证来源」或不展示。这样可把「展示出来的来源」可访问率
   从 59.6%（脚本口径）/94.1%（乐观口径）提升到接近 100%，满足用户对「点得开」的预期。
2. **不直接采用模型输出的 URL 文本**：以 Search 返回的结构化结果为准（URL 白名单），模型只允许引用检索结果
   中出现的 URL；对模型改写/截断的 URL 做字符串比对并回退到检索原文（本轮 1 条改写 + 2 条截断）。
3. **来源真实性校验**：按 URL 身份（忽略 query/fragment）与 Search 结果比对，不一致即标记/丢弃；
   这与本报告 §2.3 口径一致，可复用。
4. **检索词增强**：quick 模式 1 组检索词在信息量大的画面（表格/图例/代码）容易泛化，建议：
   从识别结果中抽取实体（模型名/标题/文件名）拼入检索词；
   或在结果质量差时自动升级为 2–3 组（deep 口径），成本可控（Search 单次 P50 ~0.3s）。
5. **四段与不确定性提示词可沿用**：`image_search.md` v1 的阶段拆法 + 「不确定处直接标注」约束在 30 张上
   100% 生效；建议保留，并在 UI 上把「不确定」高亮，避免过度 hedging（26/26 非标记图也标注不确定，
   可考虑区分「未识别」与「检索未佐证」两类标注）。
6. **网络不可达不代表来源无效**：生产环境应区分「链接失效」（404/410）与「本机网络/反爬不可达」，
   只在确认失效时降权，避免误伤 GitHub/HF 等来源。
