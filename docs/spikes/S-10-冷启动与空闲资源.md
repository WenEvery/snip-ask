## 3 测量口径（可复现定义）

### 3.1 冷启动「到托盘可交互」

- **定义**：`Process.StartTime`（内核记录的进程创建时间，UTC，精度 ~ms）→ 应用日志中出现
  「框选 AI 初始化完成（skeletonMode = …）」行的时间戳（`tracing` 默认格式自带 RFC3339 微秒时间戳）。
- **为什么该时点代表「托盘可交互」**：`src-tauri/src/app/lifecycle.rs::setup` 顺序为
  路径 → 日志 → `AppState` → **创建托盘** → **注册全局热键** → 预创建隐藏窗口 → 引擎状态 → 首启判定 → 更新检查，
  最后才输出「初始化完成」。因此该行时间等价于「托盘 + 热键 + 窗口均已创建」的应用内可观测时点；
  同批次 S-16 的 EnumWindows 实测也证实此时 `tray_icon_app` 与 `global_hotkey_app` 窗口存在。
- **附加证据**：每次运行日志中不得出现「托盘创建失败 / 全局热键注册失败」；每次运行后用 `RegisterHotKey(Ctrl+Q)`
  探测是否已被应用占用（Win32 `1409` = 已被注册）。
- **不依赖实时轮询**：见 §6.1 的踩坑——应用持有日志文件句柄期间，`Get-ChildItem` 的 `Length/LastWriteTime`
  可能陈旧；因此检测采用「以 `FileShare=ReadWrite` 直接读文件 + 只接受行内时间戳 ≥ 本次进程创建」的解析方式，
  与最终落盘内容一致、可复核。

### 3.2 空闲内存

- **主进程（判据）**：`Get-Process` 的 `WorkingSet64`（工作集）、`PrivateMemorySize64`（提交私有字节），
  以及 `Get-Counter '\Process(snip-ask)\Working Set - Private'`（私有工作集，最接近任务管理器「内存」列）。
- **进程树（补充参考）**：主进程 + 其 `msedgewebview2.exe` 子进程（WebView2 运行时）WorkingSet 合计。
  **阈值 120MB 的验收口径取主进程**；进程树数值单列，原因见 §6.3（WebView2 是多进程架构，子进程是否计入「应用内存」
  取决于任务管理器分组口径，本记录不擅自选择，给出两套数字）。
- 采样时机：启动 → 日志就绪 → **预热 60s**（让 WebView2 完成首屏/缓存）→ 每 5s 采样，共记录 30 分钟序列。

### 3.3 空闲 CPU

- 口径：`sum(process.TotalProcessorTime)`（主进程 + 进程树）相邻两次采样的 **CPU 时间差 / 墙钟差 / 逻辑核数(16) × 100%**，
  即「占总 CPU 百分比」，与任务管理器「进程」页 CPU 列同口径；同时给出「占单核百分比」（= 差值/墙钟×100）。
- 采样：30 分钟、每 5s 一次（采样本身耗时从间隔中扣除，实际周期 ≈5s）；首个样本仅作为差分基准，不参与统计。
- 阈值：**平均 < 0.5%（占总核）**；同时报告 P95/max 以观察瞬时抖动。
- 负载基线：每样本记录系统总 CPU（`\Processor(_Total)\% Processor Time`）、可用物理内存；采样前后扫描进程，
  确认无 `cargo/rustc/llama/python/onnx` 等重负载；`.verify/p1/quiet/startedAt` 标记安静窗口。

### 3.4 测量顺序与环境保护

1. 确认 `node scripts/spikes/applab/applab.mjs status` 空闲、`Get-Process snip-ask` 为 0、无 build/bench 锁；
2. 放置 `.verify/p1/quiet/startedAt`（owner/task/startedAt/expectedEndBy/plan），通知 lead；
3. 清理 app-runtime 会话遗留的 **orphan Vite dev server**（端口 `::1:1420`，18:49 启动、空闲 0%；lead 确认可杀），
   避免它影响 debug 对照与空闲采样；
4. 顺序：release 稳态冷启动 N=10 → release 首次启动对照 N=3 → debug 对照 N=10 → release 空闲 30 分钟 →
   debug 空闲 5 分钟（补充）→ 清理（停止应用、删除 quiet 标记）。

## 6 关键发现

### 6.1 「文件被占用期间目录元数据陈旧」踩坑与修复（真实、可复现）

首次实现用 `Get-ChildItem` 的 `Length/LastWriteTime` 判断日志增量，10 次冷启动只命中 **1 次**（首次运行，日志文件是新建的）。
诊断复现：应用运行期间，日志文件已写入新行，但 `Get-ChildItem` 返回的 `Length` 与 `LastWriteTime` 保持不变（NTFS 在文件被
独占打开期间不保证及时更新目录项元数据）；而用 `[IO.File]::Open($path,'Open','Read','ReadWrite')` 直接读取**能立即读到新内容**。
修复：改为「整文件读取（FileShare=ReadWrite）+ 只接受行内时间戳 ≥ 本次进程创建时间」解析，修复后 release 10/10 全部命中。
该结论同样修正了 S-16 首次启动测量时「实时轮询未命中」的现象（S-16 记录按日志时间戳取值，结论不变）。

### 6.2 debug 与 release 的冷启动差异（口径说明）

- release：前端资源内嵌在 exe（`dist` 打进二进制），启动时无网络/文件服务依赖。
- debug：`beforeBuildCommand` 的产物不参与 debug 运行，WebView 加载 `http://localhost:1420`（Vite dev），
  首屏需 Vite 转换模块、且受 Vite 进程调度影响；首次运行最慢（1812ms）。
- 因此 S-10 验收口径以 **release** 为准；debug 仅用于开发期回归参考（建议阈值不变时以 release 门禁，debug 观察趋势即可）。

### 6.3 内存口径差异（主进程 vs WebView2 进程树）

- 主进程（Rust/Tauri 壳）WorkingSet 约 36–40MB；但 WebView2 运行时是多进程架构（浏览器进程、渲染进程、GPU 进程、
  utility 进程等），空闲时仍可能有 1–7 个 `msedgewebview2.exe` 子进程，进程树 WorkingSet 合计可达数百 MB。
- 任务管理器对「应用」的分组行为与 WebView2 子进程归属在不同 Windows 版本/设置下不一致；因此本记录给出两套数字：
  **主进程（判据，≤120MB 的通常语义）** 与 **进程树（补充）**，并建议在验收文档中明确「空闲内存」= 主进程私有工作集。
- 若产品口径要求「进程树总量 ≤120MB」，则当前实现**不达标**（WebView2 本身即超过），需要产品决策（如不纳入 WebView2、
  或改为「主进程 + 渲染进程」等自定义口径）——列入 §8 遗留。

### 6.4 其它观察

- 空闲 CPU 的主要来源是 **WebView2 定时器/合成器**与 Win32 消息循环；纯 Rust 壳本身接近 0。
  因此「占总核 0.5%」在 16 逻辑核机器上对应单核约 8%，属较宽松口径；本记录同时给占单核百分比便于横向比较。
- release 空闲 30 分钟期间无日志异常、无崩溃、无进程退出；Ctrl+Q 热键保持注册（每次冷启动运行后探测均为 1409）。

## 7 判定

- 冷启动（release，N=10）：P50 **787.2ms** / P95 **858.3ms** / max **876.8ms** → **≤1.5s 达标**；
- 空闲内存（release，主进程口径）：WorkingSet max **36.80 MiB ≤ 120MB**、Private WS max 10.20 MiB → **达标**；

## 8 遗留与风险

| # | 遗留项 | 说明/建议 |
| --- | --- | --- |
| 1 | **空闲内存口径未在产品文档固化** | 建议明确「空闲内存 = 主进程私有工作集（≤120MB）」；若要求含 WebView2 进程树，需重新定义阈值（当前进程树 >120MB 属 WebView2 架构成本，非应用泄漏）。 |
| 2 | 仅本机（i7-12650H/16 逻辑核）测量 | 低配/8GB 机型、不同电源计划（节能/高性能）、机械硬盘冷启动未覆盖；建议在 8GB 参考机复跑本脚本。 |
| 3 | 冷启动为 OS 文件缓存已热 | 未做「重启后首次启动 / 清理 standby list」的真冷启动；如需可加 `EmptyStandbyList` 或重启后测量（本机未做，避免影响其它验证）。 |
| 4 | 未测长时间使用后的空闲 | 本次为「启动后静置」空闲；用户先框选/OCR/对话后回到空闲的稳态内存可能更高（例如 OCR/WebView 缓存），建议补「使用后 5 分钟静置」场景。 |
| 5 | 睡眠/唤醒、锁屏后恢复未测 | 托盘应用常驻场景相关，建议后续加电源事件回归。 |
| 6 | debug 对照超阈值 | 非验收口径；如要开发期门禁，建议单独设 debug 阈值或改用 release 版做启动回归。 |
| 7 | 采样期间系统常驻负载 ~7–15% | 来自 DSH/Edge 等常驻进程（Lead/用户环境），已记录基线；应用 CPU 按进程树折算，不受影响，但极小值的绝对精度受采样粒度限制（5s）。 |
| 8 | 空闲 CPU「0.5%」的核数口径 | 本记录按「占总核」计（任务管理器口径）；若按「占单核」则阈值等价于 0.5%/核，会严格 16 倍，需产品确认。 |
