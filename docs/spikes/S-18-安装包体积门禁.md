## 6 「含/不含模型」两种配置口径

S-18 清单阈值为「主安装包 ≤25MB（不含模型）；含模型 ≤60MB」，但**未定义「模型」指哪类模型**。本记录按两种口径分别给出事实：

### 6.1 口径 A：模型 = OCR 模型（PP-OCRv4 ONNX，S-02/S-03 实际基准所用）

| 文件 | 字节 | MiB |
| --- | --- | --- |
| `ch_PP-OCRv4_det_infer.onnx` | 4,745,517 | 4.526 |
| `ch_PP-OCRv4_rec_infer.onnx` | 10,857,958 | 10.355 |
| `ch_ppocr_mobile_v2.0_cls_infer.onnx` | 585,532 | 0.558 |
| **合计** | **16,189,007** | **15.44** |

- 含 OCR 模型安装包估算：**≈11.8–18.0 MiB**（下界按 ONNX 经 NSIS LZMA 压缩 ≈0.6 比例、上界按完全不压缩；
  **未真实打包**）。两种估算均 **≤60MB**，上界也 **<25MiB**。
- 结论：若产品选择内置 OCR 模型，S-18「含模型 ≤60MB」**成立**，且不影响 25MB 主阈值（但会增加用户下载量，
  仍建议按需下载/随首启下载，与模型管理一致）。

### 6.2 口径 B：模型 = 本地 LLM（GGUF，`resources/models.manifest.json` 4 条）

| 模型 | 文件 | sizeBytes | MiB |
| --- | --- | --- | --- |
| hy-mt-1.8b-q4 | HY-MT1.5-1.8B-Q4_K_M.gguf | 1,133,080,512 | 1,080.6 |
| qwen3-4b-q4 | Qwen3-4B-Q4_K_M.gguf | 2,497,280,256 | 2,381.6 |
| opus-mt-zh-en | （ct2-int8，官方暂无产物） | 314,572,800 | 300.0 |
| qwen2.5-0.5b-instruct-q4 | qwen2.5-0.5b-instruct-q4_k_m.gguf | 491,400,032 | 468.6 |
| **合计** | — | **4,436,333,600** | **4,230.8（4.13 GiB）** |

- **「含模型 ≤60MB」在本口径下不成立**：合计约 4.13 GiB；即使只带最小的 Qwen2.5-0.5B（468.6 MiB）也超 60MB 约 7.8 倍。
- 当前产品设计即**模型不随安装包分发**（`docs/spikes/S-08`：按需下载 + Range 断点续传 + SHA256/大小校验；
  `models.manifest.json` 顶部也注明「模型文件不随安装包分发，由用户按需下载」）。
- 结论与建议：**门禁口径应写成「不含模型」**；若未来需「含 LLM 模型」发行版，60MB 阈值不可达，需改为
  「安装包门禁 + 首启模型下载量」分开验收（或走云端）。

### 6.3 阈值单位说明

清单写「25MB」，本记录与实现按 **25 MiB**（1 MiB = 1,048,576 B）执行，比十进制 25MB（23.84MiB）略宽松 ≈0.4%；
实测 2.569 MiB 距两种口径都极远，结论不受影响。CI 脚本 `-ThresholdMiB 25`，如要与十进制对齐可改 23.8。

## 7 CI 体积门禁落地

改动仅 `.github/workflows/ci.yml`（本任务唯一允许修改的仓库文件）：

- 新增 job `bundle`（`windows-latest`，`timeout-minutes: 60`）：
  checkout → pnpm/Node 22 → Rust stable + `Swatinem/rust-cache`（workspaces: src-tauri）→ `pnpm install --frozen-lockfile`
  → `pnpm tauri build` → PowerShell 体积检查 → 归档体积基线 artifact；
- 体积检查复用 `scripts/spikes/s10_s16_s18/check_bundle_size.ps1`：
  - 取 `src-tauri/target/release/bundle/nsis/*-setup.exe` 最新一个，超过阈值 `exit 1`（CI 失败）；
  - 生成 `.verify/ci/volume_baseline.json`（commit/工具链/产物 SHA256/大小/时间）；
  - 与仓库内 `docs/spikes/data/s16_s18/volume_baseline.json` 对比并打印 ΔMiB / Δ%；
  - 产物缺失时 `exit 2`（构建失败即失败，不静默放行）；
- 优雅跳过（降级路径）：仓库变量 `SKIP_BUNDLE_GATE=true` 时整个 job 跳过；脚本内亦支持环境变量
  `SKIP_BUNDLE_SIZE_GATE=true` 直接跳过并打印说明；
- artifact：`bundle-size-baseline`（`.verify/ci/volume_baseline.json`，失败也归档，`retention-days: 30`）。

## 8 遗留与风险

1. **CI 未在真实 GitHub Actions 上实跑**（本机无 runner）：`pnpm tauri build` 需要 Rust 工具链、WebView2、以及
   Tauri CLI 首次自动下载的 **NSIS**（网络到 GitHub releases）；若 runner 网络受限或 NSIS 安装失败，`bundle` job 会红。
   首次 push 后需观察一次；必要时用 `SKIP_BUNDLE_GATE=true` 临时放行并在本记录补充风险说明（不得长期静默跳过）。
2. **首次 CI 构建耗时**：冷缓存下 release profile（LTO + codegen-units=1）在 windows-latest 预计 10–20 分钟，
   `timeout-minutes: 60` 留足余量；`rust-cache` 会缓存 `target`，后续构建明显加快。
3. **趋势自动化程度**：CI 只归档本次基线 artifact，不会自动 commit 更新仓库内基线 JSON（避免 CI 写仓库）；
   趋势对比以仓库内基线为锚，需人工在版本发布/体积变化时更新 `docs/spikes/data/s16_s18/volume_baseline.json`。
   后续可选：加 release tag 时用 bot 提交基线。
4. **「含模型」未真实打包**：§6.1 的含 OCR 模型体积是估算（真实构建可能因压缩率不同 ±20%）；若产品决定内置，
   需按同一脚本再真实构建一次并更新基线。
5. **只门禁 NSIS setup**：不门禁主 exe、MSI（当前 `targets=["nsis"]`，无 MSI）；若未来加 MSI/portable target 需扩展脚本。
6. **阈值单位**：25MB vs 25MiB 的 ≈0.4% 差异见 §6.3，当前余量极大不影响结论。
7. **构建锁只覆盖本机并行验证**：CI 无此锁；本地多人并行时若有人绕过 `build.lock` 直接构建，会互相干扰
   （属纪律问题，非 S-18 缺陷）。
8. **签名状态**：安装包未签名（`NotSigned`，见 S-16），签名后体积会略增（证书链不打包、影响极小），届时更新基线。
