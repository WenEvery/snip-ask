## 2 被测口径

**四阶段**：①视觉识别（图片→文字/结论）→ ②生成检索词 → ③Search（quick 1 组 count=5；deep 3 组 × count=10）→ ④摘要（结论+来源）；deep 额外 ③b Fetch 2 条正文。

| 项 | quick | deep |
| --- | --- | --- |
| 检索词 | 1 组（来自阶段①输出） | 最多 3 组 |
| Search | count=5，need_content=false | 3 次 × count=10（共 30 条结果） |
| Fetch | 不抓取 | 并发抓取前 2 条 URL 正文（`ThreadPoolExecutor(2)`，单次 timeout 8s、重试 1 次） |
| 摘要输入 | 识别结果 + 5 条结果摘要 | 识别结果 + 30 条结果摘要 + 2 条正文节选（每条 ≤1200 字符） |
| 阈值（P95） | **≤10,000 ms** | **≤25,000 ms** |

- 提示词：`resources/prompts/image_search.md`（版本 1，sha256 `03a119ed…3aad`）正文按阶段拆分（阶段①识别+检索词；阶段④结论+来源），与 phase-1 相同。
- 运行：每档 warmup 2 + 实测 20 次；失败按生产策略重试（429/5xx/超时退避 ≤2 次；404 不重试）。
- 计时：每阶段 client 侧耗时；端到端 = 四阶段 + 编排开销的墙钟时间。

## 4 Search / Fetch 单独时延（各 20 次）

`python scripts/spikes/s05_s06/bench_deepseek_tools.py --runs-search 20 --runs-fetch 20 --count 5 --fetch-urls <稳定 docs URL 列表>`

| 接口 | P50 | P95 | max | 失败 | 备注 |
| --- | --- | --- | --- | --- | --- |
| Search（count=5） | **292.01 ms** | **413.34 ms** | 698.47 ms | 0/20 | 均 200，无空结果；QPS 限制 100 |
| Fetch（4 个 docs URL 轮换） | **83.94 ms** | **3,196.66 ms** | 3,719.32 ms | 0/20 | 全部返回正文；P95 被 1 个较重文档页拉高；QPS 限制 25 |

对照证据（同脚本首轮，用 Search 返回的任意 URL 抓取）：Fetch **8/20 为 404、P95 17,944 ms** → **检索结果 URL 质量决定 Fetch 时延与成功率**，
生产实现必须：① 校验 URL/跳过 404；② Fetch 设置短超时（建议 5–8s）；③ 失败回退 Search 摘要，不阻塞摘要阶段。
本轮 image_search 流水线已按「并发 2、单次 8s、重试 1 次、失败回退摘要」实现，因此 deep P95 仍为 8.29s。

## 5 失败与错误码处理

- 流水线 40 次（quick 20 + deep 20）**0 失败**；HTTP 状态：流水线内部全部 200。
- DeepSeek 工具 API 错误码：400/401/402/403/404/408/413/429/500/504；脚本对 **408/429/5xx/网络超时**退避重试（`0.5s/1s`，≤2 次）并记录 `attempts`；
  **404 不重试**（示例：Search 结果中的 `youpin.bochao.com.cn/...pdf` 返回 404，直接跳过）。
- 400（参数/格式）、401（Key）、402（余额）、403（权限）不重试，直接记录并失败；本任务 Key 状态正常，未出现 401/402/429。
- 计费：Search 有结果、Fetch 有正文才计费；本轮 quick 20 + deep 20 + standalone 40 次请求均成功（成本按官方价目表估算，本报告不展开）。

## 6 结论与处置（S-06 已解除 BLOCKED）

1. **验收结论**：quick P95 **6.01s**、deep P95 **8.29s**，均显著低于阈值 → **S-06 DONE**；可以更新 `docs/技术验证清单.md` 与 `S-06` 任务状态（本任务不修改清单文件，由 Lead 统一回写）。
2. **实现建议（给应用集成）**：
   - 视觉与摘要均使用 `deepseek-flash` + `thinking:{"type":"disabled"}`（否则首字/阶段耗时被 reasoning 推高，参见 S-05 云端实测）。
   - Search 用 `POST /v1/tools/search`（quick count=5；deep 每组 count=10，按 `modes.deepBudget.search=3` 执行）。
   - deep 的 Fetch 并发 2、单次 timeout 5–8s、失败回退摘要；对 404/连接超时快速失败，避免尾部 20s+。
   - 备选：deep 可改用 Search `need_content=true` 一次拿到正文（省一次往返、少一个尾部来源），需另测时延/成本。
   - 成本观察：quick tokens/次 ~2.8k、deep ~6.5k（含 30 条结果摘要与图片 token）；可对 deep 结果去重/压缩摘要降低 token。
3. **风险**：deep 长尾（本次 max 23.1s，仍 <25s）由失效/慢 URL 引起；若生产不限制 Fetch 超时，存在超阈值风险。来源真实性与幻觉抽检列入 S-12。
