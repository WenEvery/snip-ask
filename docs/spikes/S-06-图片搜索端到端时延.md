## 2 被测口径

- **链路**（4 个阶段，与产品设计一致）：①视觉识别（图片→文字/结论）→ ②生成检索词 → ③Search（quick 1 次、
  deep 2–3 次）→ ④摘要（结论 + 来源）。
- **提示词**：`resources/prompts/image_search.md`（版本 1，sha256 `03a119ed…3aad`）正文按阶段拆分：
  阶段①只要求输出「识别结果」「检索词」，阶段④把识别结果 + 检索词 + 真实检索结果交给同一模型输出「结论」「来源」。
  脚本 JSON 中记录 `prompt_sha256` 与拆分说明（`config.prompt_derivation`）。
- **模型接口**：OpenAI 兼容 chat/completions，vision 消息用 base64 data URL；检索服务由
  `SNIPASK_BENCH_SEARCH_PROVIDER` 选择 `tavily` / `serper`（也可 `none`=缺省，此时直接 BLOCKED）。
- **计数**：每档 warmup 1 + 20 次实测，记录端到端 P50/P95/max、分阶段时延（vision / query_gen / search / summary）、
  失败率、token 用量、检索结果条数。
- **判定阈值**（`docs/技术验证清单.md` §2）：快速模式 **≤10s**；深度模式 **≤25s**（P95）。
- **无 Key 时的行为**：脚本打印 BLOCKED（缺哪些变量、解锁步骤）并以**退出码 2** 结束，不产生假数据；
  `--mock-self-check` 用 mock 视觉 + mock 检索跑通流水线，输出 `meta.mode="MOCK_SELF_CHECK"`、
  判定为 `MOCK_SELF_CHECK_OK`，**mock 数字不作 DONE/FAILED 依据**（mock 检索 URL 使用 `example.invalid`，
  检索摘要写明「不可信」）。

## 4 结果与阈值对比

| 档位 | 阈值（P95） | 真实测量 | 判定 |
| --- | --- | --- | --- |
| 快速 quick | ≤10,000 ms | **无 Key，未测** | BLOCKED |
| 深度 deep | ≤25,000 ms | **无 Key，未测** | BLOCKED |

**无法给出真实数值，也不臆测 DONE/FAILED。** 以下为供拿到 Key 后验证的预算与风险分析（假设值，明确标注为预算）：

| 阶段 | quick 预算（2 次模型调用 + 1 次检索） | deep 预算（2–3 次模型调用 + 2–3 次检索） |
| --- | --- | --- |
| ①视觉识别（含图片上传 + prefill） | 2–5 s | 2–5 s |
| ②生成检索词（本地解析） | <10 ms | <10 ms |
| ③Search（每次检索 API） | 0.5–2 s × 1 | 0.5–2 s × 2–3（串行 ≈1–6 s） |
| ④摘要 | 2–5 s | 2–6 s |
| **合计** | **约 4.5–12 s（10s 阈值处于边界，有超标风险）** | **约 7.5–17 s（通常可达标；检索串行且慢时接近 25s）** |

风险与缓解：

1. quick 10s 阈值本身偏紧：vision 端点冷启动/图片 prefill 大时单次即 4–6s；建议实测后若超标，
   把「生成检索词」与「视觉识别」合并为一次调用（当前实现已合并为阶段①的两次输出段落），并让摘要复用识别文本，
   或对 quick 采用更小/更快的视觉模型。
2. deep 的检索次数应按 `modes.deepBudget.search`（默认 3）执行；串行 3 次检索在慢网络下可能吃掉 6s。
   建议检索并发（`asyncio.gather` 或线程池）并严格限制 `max_results=5`；摘要只喂 top 结果，控制 prefill。
3. 视觉模型可能不遵守四段格式 → 解析失败率高；脚本已把原始输出与解析结果都落盘，复跑时应同时看
   `records[].vision_output` / `summary_output` / `sources`，不能只看耗时。
4. 来源真实性（prompt 要求只引用检索结果中的真实 URL）需人工抽检；mock 数据的 `example.invalid` 不可信。

## 5 解锁步骤：拿到 Key 后 15 分钟复跑清单

| 时间 | 操作 |
| --- | --- |
| 0–2 min | 准备凭据：任一 OpenAI 兼容 vision 端点 Key（OpenAI `gpt-4o-mini`、DashScope `qwen-vl-max` 等）+ 检索服务 Key（Tavily 或 Serper）。**无需改代码。** |
| 2–3 min | 设置环境变量（见下）。 |
| 3–5 min | 先跑小样本冒烟：`--modes quick --runs 2`，确认视觉接口接受图片、检索返回 200、四段解析正常；查看 JSON 的 `vision_output`/`sources`。 |
| 5–8 min | quick 正式 20 次：`--modes quick --runs 20`（每次约 5–10s，合计约 2–3 分钟）。 |
| 8–14 min | deep 正式 20 次：`--modes deep --runs 20`（每次约 8–18s，合计约 3–6 分钟）。 |
| 14–15 min | 汇总：脚本自动输出 P50/P95/max 与 DONE/FAILED；把 `docs/spikes/data/s05_s06/` 中新增 JSON 与本文件 §4 更新（含真实数字与模型/检索服务名）。 |

```powershell
$env:SNIPASK_BENCH_VISION_BASE_URL = "https://api.openai.com/v1"   # 任意 OpenAI 兼容 vision 端点
$env:SNIPASK_BENCH_VISION_MODEL    = "gpt-4o-mini"                 # 或 qwen-vl-max 等
$env:SNIPASK_BENCH_VISION_API_KEY  = "<Key>"
$env:SNIPASK_BENCH_SEARCH_PROVIDER = "tavily"                      # 或 serper
$env:SNIPASK_BENCH_SEARCH_API_KEY  = "<检索 Key>"

# 冒烟 → quick 20 次 → deep 20 次（也可一次 --modes quick,deep）
python scripts/spikes/s05_s06/bench_image_search.py --modes quick --runs 2
python scripts/spikes/s05_s06/bench_image_search.py --modes quick --runs 20
python scripts/spikes/s05_s06/bench_image_search.py --modes deep  --runs 20
```

可选参数：`--image <path>`（换测试截图）、`--lang zh-CN`、`--runs`、`--timeout`、
`--max-queries-deep 3`。脚本输出 JSON 到 `.verify/spikes/S-05-S-06/raw/`，并在 stdout 打印分阶段 P50/P95。

**注意**：`SNIPASK_BENCH_SEARCH_PROVIDER=none` 时脚本会直接 BLOCKED（纯 mock Search 不满足「1 次真实 Search」
验收口径）；同样，若只配 vision Key 而没配检索 Key，也按 BLOCKED 处理，不生成假来源。
