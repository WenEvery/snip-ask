### 1.2 致命缺口 F1：真实 IPC 下追问**必然** SA-1099

这是本报告最重要的发现。推导链（每一环都有 file:line）：

**路径 A（用户实际时序：回答已完成后再追问）**

1. 首轮 `menu_execute` → `task_runner::spawn` 把任务登记进 `TaskStore`（`task_runner.rs:66-76`）。
2. 任务成功后：先 `emit_task_done`（`task_runner.rs:118-127`）→ `session.task_finished()`（`:129-131`，`Executing→ShowingResult`）
   → **`tasks.remove(&task_id)`（`:132-135`）**。失败/取消路径同样移除（`:167-170`、`:192-195`）。
   即：**`TaskStore` 只保留「进行中」任务，已完成任务的 id 不在表里**。
3. 前端在收到 `task:done` 后让用户输入追问，调用 `task_followup({ task: ctx.task, text })`（`ResultWindow.tsx:237`）。
4. 后端第一步就按 `task` 查所属会话：`tasks.session_of(&task)`，查不到即返回
   `AppError::invalid_state("任务 {task} 不存在")`（`action.rs:121-126`）。
5. `invalid_state` → **`SA-1099`**（`contract/errors.rs:27`、`:260-263`；用户可见 message 为默认「当前状态不允许该操作」，detail 里是「任务 … 不存在」）。
6. 前端把该错误渲染成整块错误区并 `setPhase("error")`（`ResultWindow.tsx:239-242`、`:277-289`），用户看到「当前状态不允许该操作 / SA-1099」。

**路径 B（流式过程中就提交，前端并未禁止）**

1. 流式期间 `sending` 在 `invoke` 返回后立即复位（`ResultWindow.tsx:234-244` 的 `finally`），输入框未随 `streaming` 禁用（`ResultFooter.tsx:33` 仅 `disabled={props.sending}`）。
2. `task` 仍在 `TaskStore` 中 → `session_of` 成功，但会话阶段是 `executing`（`action.rs:133-138` 要求 `showingResult`）→ 同样 `SA-1099`。

**路径 C（微秒级竞态窗口，不构成可用路径）**

`emit_task_done`（`:118`）→ `task_finished`（`:129`）→ `tasks.remove`（`:132`）之间存在一个窗口：
此时阶段已是 `showingResult` 且任务还在表里，理论上可成功。但前端从收到 `done` 事件到用户键入文字至少数百毫秒，
**该窗口不可能被用户命中**（复现器场景 C 明确验证：窗口内成功、窗口后立即失败）。

**后端虽保留 `Session.task_ids` 这个 id 列表，但没有「最近一次任务」的便捷访问，也没有回答正文留存**：
`session.task_ids` 只累积 id（`session.rs:72-73`、`:232`），`TaskStore` 无「最近完成」缓存（完成即移除），
`history_repo` 不提供按 task 反查 session 的运行时 API（只在落库时写）。因此即使把查找改成「遍历 `task_ids`」，
也只能确认 id 归属，**拿不到上一轮回答内容**（正文注入是另一项改动，见 F2/G2）。

> **结论**：在当前代码路径下，真实 IPC 的追问在「完成后 / 流式中 / 失败后」三种情形返回的都是 `SA-1099`。
> 复现器 4/4 场景通过，见 `logs/repro_run.log`；断言见 `verify.ps1` B 组第 19 条（`tasks.remove` 计数 ≥ 3）。

**修复量极小但不是可选项**：把「按 task 找会话」改为「以当前活动会话为准，并用 `session.task_ids` 校验该 task 属于本会话
且为最近一次任务」（`session` 本身保留全部 `task_ids`，`session.rs:154-162` 提供 `current_selection`，也可新增 `last_task_id()`）。
这属于 P0 阻塞项；不做它，后面所有多轮设计都无法验收。

> **文档状态需要修正**：`docs/实施架构.md:208` 把 M13 结果窗的「追问」标为 ✅（「流式渲染、来源、追问、复制」），
> 与本节结论不符。建议改为「追问 UI 骨架 ✅ / 多轮链路 ❌（task-9 待实施）」，避免后续排期误判为已完成。

### 1.3 契约与事件核实

- 命令表第 7 条：入参 `task: TaskId`, `text: string`，返回新 `TaskId`，错误码 `SA-1099, SA-3001…`，
  副作用为「新任务 id；`task:started` + 同上流式事件」（`docs/接口契约.md:289`）。
- 状态规则：`task_followup` 只在 `showingResult` 态合法（`:271`）；`menu_execute` 在 `menu` 或 `showingResult` 态合法（后者用于「重答」）。
- 事件载荷：
  - `TaskStartedPayload { task, session, action, mode, engine }`（`contract/types.rs:358-372`；TS 侧 `src/shared/contract/types.ts:273-279`）——
    **没有** `parent` / `kind` / `conversationId`，因此前端无法从事件层面判断「这是首轮还是追问」。
  - `task:delta` 按 `{ task, kind, chunk }` 过滤（`contract/events.rs:128-137`），前端用 `taskIdRef.current` 丢弃旧任务 delta（`ResultWindow.tsx:90`）——
    这套「单活动任务」的过滤机制在线程化后仍可复用（只流式最后一条）。
  - `task:done` 载荷含 `usage/latencyMs/engine/sources`（`types.rs:374-388`），但**不含回答正文**，正文只能靠前端累积 delta。
- 版本策略：`IPC_CONTRACT_VERSION = 1`（`contract/events.rs:16`）；契约 §16 允许「新增可选字段（前端容忍未知字段，后端提供默认值）」
  （`docs/接口契约.md:584-585`）——因此**加 `parent` 属于向后兼容的增量**，不必递增契约版本，但需改契约文档、Rust/TS 类型与修订记录。
- 结果窗是常驻窗口（惰性创建、只隐藏不销毁：`app/windows.rs:205-260`），现有 React 状态在多次会话间会残留，
  `task:started` 时清空（`ResultWindow.tsx:81`）是当前的复位手段——线程化后要重新定义「何时清空」。

### 1.5 提示词现状（`followup.md` 评估）

`resources/prompts/followup.md` 正文（`:8-32`）质量不错，方向正确：
角色声明「前一轮任务已经给出回答，用户基于同一份框选内容继续提问」、要求「不重复上一轮」「发现错误先写更正」
「300 字以内」「不编造来源」等；模板头注释（`:2`）明确 `{context}` = **先前任务的动作、模式与已生成回答摘要**。

问题在于**实现没有兑现模板语义**：

1. `commands/action.rs:147` 传入 `context = selection.preview`（选区 OCR 文本，`selection.rs:69-76` 合并的识别文本），
   不是上一轮回答。模型看到的是「原始选区 + 追问」，**完全不知道上一轮答了什么**——
   于是「不要重复上一轮内容」「发现前一轮有误写更正」这类要求全部落空。
2. `{question}` 只放用户追问文本，没有「首轮问题/回答」结构；`followup.md` 也没有 `{history}` 之类的插槽。
3. `LlmRequest` 只有单个 `prompt: String`（`llm_gateway.rs:47`），**没有 messages 数组**，无法表达 system/user/assistant 多轮结构；
   真实网关若要支持多轮，需要扩展该结构（`llm_gateway.rs:1-11` 的 `TODO(real)` 也只列了单轮 SSE 解析）。
4. 骨架网关**忽略 `prompt`**：`placeholder_text(request.action, &request.input_text, request.mode)`（`llm_gateway.rs:138`），
   即骨架模式下即使修好 prompt，输出仍是固定占位文本——**无法用骨架模式验收提示词效果**，需要 fake gateway 捕获请求或先落真实网关。
5. 维护注释剔除机制正常（`prompt_engine.rs:59-74`），变量白名单 `KNOWN_VARS` 含 `question/context`（`:19-28`），
   若新增 `{history}` 变量需同步该白名单与模板测试（`prompt_engine.rs:210-244` 要求每个模板可渲染）。
6. 主路径 `render_prompt` 里把 `question/context` 置空（`action.rs:211-212`），说明设计上「主路径提示词不含追问变量」，
   追问必须走独立渲染——这条边界目前是清楚的。

### 1.7 持久化与「历史里能否关联同一对话」

现状（`migrations/001_init.sql`）：

```sql
sessions(id, started_at, rect, has_text, ocr_text, app_exe)          -- :19-26
tasks(id, session_id, action, mode, engine, status, first_token_ms,
      total_ms, tokens_in, tokens_out, cost_est, error_code, created_at) -- :29-43
usage_daily(day, tasks, tokens_in, tokens_out, cost_est)             -- :46-52
-- 索引：idx_tasks_session_id / idx_tasks_created_at / idx_sessions_started_at  -- :54-56
```

事实核对：

1. **能按 `session_id` 把同一次框选内的所有任务（含追问）关联起来**——这是目前唯一的「对话线索」。
   但追问任务以 `action=answer` 落库（`action.rs:160` + `task_runner.rs:136-146`），**与首轮解答无法区分**；
   也没有 `parent_task_id`，无法还原先后顺序（同毫秒 `created_at` 还可能并列）。
2. **不能恢复对话内容**：`tasks` 无正文列；`history_repo` 没有读取正文的 API（唯一查询是 `SELECT id FROM tasks WHERE session_id`，`history_repo.rs:298`）；
   前端也没有历史页/恢复入口（`src/windows/main/**` 只有设置与引导）。
3. **连选区原文都没落库**：`sessions.ocr_text` 列存在，但 `capture_freeze` 调用 `record_session(..., ocr_text=None, ...)`（`capture.rs:115-122`），
   历史库当前只存元数据与用量，这与「日志禁止记录 OCR 原文」（`history_repo.rs:6`）的隐私姿态一致。
4. 迁移框架只有一个 `001_init.sql`（`history_repo.rs:17` 的 `include_str!` + `:67` 的 `execute_batch`），
   `schema_migrations` 表仅写入 version=1（`001_init.sql:10-16`），**没有 002 迁移的执行框架**。
5. 清理策略：按 `retention_days` 删 `tasks`/`sessions`（`history_repo.rs:244-253`）、按 `max_entries` 裁剪（`:254-261`）、
   `clear()` 删三表（`:265-274`）；`history.enabled=false` 时全 no-op（`:40-60`、`:91-93`）。
   默认值：enabled=true / maxEntries=1000 / retentionDays=90（`contract/config.rs:614-635`）。

> **结论**：历史里**能按 `session_id` 关联任务元数据，但不能恢复对话，也没有任何「对话」概念**。
> 完整版需要新增 `messages` 表（+ 可选的 `parent_task_id`），并扩展迁移框架、清理与隐私门禁。

## 2 差距分析：真实多轮对话需要什么

> 记号：Gx 为差距项；「现状 → 需要」两列直接对应 §1 证据。

### G1 对话/线程数据模型（缺失，高）

- 现状：会话（sessions）本身承载「一次框选」的生命周期；任务（tasks）只记元数据；无 messages/thread。
- 需要：**至少**能表达「会话内的有序消息序列」：`role(user/assistant/system)`、正文、所属 task、序号、状态（streaming/done/cancelled/error）。
- 影响：没有它，历史恢复、跨窗口线程、审计、成本归集都做不了；但**MVP 可以先用内存结构**（见 §3.2），不阻塞。
- 设计判断：**不需要新增 conversationId**——`SessionId` 天然就是「一次框选对话」的作用域；追问不跨会话。
  需要的是 `messages(session_id, seq, role, content, …)` 与任务级 `parent_task_id`。

### G2 上一轮 Q&A 注入（缺失，高）

- 现状：`{context}` 被错填为选区文本（`action.rs:147`）；`LlmRequest` 单字符串，无 messages。
- 需要（MVP）：把「选区原文 + 最近 N 轮 user/assistant 文本」拼进 followup 提示词（`{context}` 语义回归），
  或（完整）改成 OpenAI 兼容 `messages[]`。
- 影响：不注入 = 名为多轮、实为单轮；模型会重复上一轮内容、无法承接指代（「它」「这个」「第二点」）。

### G3 上下文窗口 / token 预算 / 裁剪（缺失，中高）

- 现状：无预算、无裁剪、无 token 计数（真实 usage 也没接，骨架固定 120/60，`llm_gateway.rs:170-182`）。
- 需要：`budget = maxTokens`（按模型上下文留出输出空间）；估算输入 token（中文约 0.6–1 token/字，可用 chars/2 粗估 + 安全系数）；
  从最旧轮次开始裁剪，保留 system + 选区 + 最近 N 轮；超长回答入库/入 prompt 前截断（如 2–4KB）；多轮成本可解释。
- 影响：不裁剪会 ① 超模型上下文直接 400；② 成本/时延随轮次近似线性增长；③ 本地小模型直接爆窗口。

### G4 UI 线程渲染（缺失，高）

- 现状：单 `text` 状态 + 单 `StreamView`，`task:started` 清空 → 覆盖。
- 需要：`turns: Turn[]`；每轮「用户气泡 + AI 气泡」；**只流式最后一条**（复用现有 taskId 过滤即可）；
  历史气泡折叠（长回答默认收起）、滚动跟随、错误气泡内联、取消气泡标记、复制「本轮/全文」。
- 影响：不改 UI，多轮只能看到最后一轮；且现有整块 error 渲染会顶掉整个对话。

### G5 事件无法区分首轮/追问（缺失，高）

- 现状：`task:started` 载荷无 `parent/kind`；追问以 `action=answer` 下发（`action.rs:160`）。
- 需要：新增可选 `parent: TaskId | null`（首轮/重答为 null，追问为上一任务 id）与可选 `kind`（或由 parent 推导）；
  前端据此：**parent=null → 重置线程；parent≠null → 追加气泡**。
- 影响：不加则前端只能靠「本地按钮意图」猜，重答/追问时序一乱就错挂气泡；历史也无法分组。

### G6 与重答/重新框选的状态机一致性（部分，高）

- 现状：`showingResult → executing` 两条路径（重答 `menu_execute`、追问 `task_followup`）都合法；
  但 `task:error` 后是 `error` 终局，重试/追问全禁；「重新框选」在结果窗**没有入口**（只有重答），只有 overlay 菜单/热键路径。
- 需要：明确并实现以下语义矩阵（§3.9 表）：重答清空线程并取消旧任务；追问追加；失败可重试（错误渲染在气泡内，不改会话终局，或允许 error→executing）；
  重新框选视为新对话（明确提示或保留历史列表）；`result_close` 关闭即结束对话（完整版可保留到历史）。
- 影响：不统一会出现「失败即报废」「重答后气泡串台」「新框选旧线程残留」三类 bug。

### G7 真实网关缺失（缺失，阻塞验收）

- 现状：`SkeletonLlmGateway` 恒定 25–40ms/块占位；真实 SSE/重试/usage/多模态全是 `TODO(real)`（`llm_gateway.rs:1-11`、`task_runner.rs:244`）。
- 需要：`LlmGateway` 真实实现（OpenAI 兼容 `/v1/chat/completions`，`stream:true`，429/5xx 指数退避 ≤2，401/402 不重试，
  解析 usage 换算 CNY，`thinking:{"type":"disabled"}` 快速模式），并支持 `messages[]`。
- 影响：**没有真实网关，本需求无法做「真实模型多轮质量」验收**；但可以用 fake gateway 捕获 prompt 做协议验收（§7.3）。

### G8 持久化能力（缺失，中）

- 现状：见 §1.7。
- 需要：`messages` 表 + `tasks.parent_task_id`；迁移框架（002）；`record_message/messages_for_session`；
  cleanup/clear/隐私开关联动；历史加载命令（只增不改）。
- 影响：MVP 可内存；完整版必须落库（否则关窗/换会话即丢）。

### G9 local vs cloud 差异与降级（缺失，中）

- 现状：`resolve_followup` 复用 Answer 路由（云端主、本地 fallback），但执行器不消费 fallback；本地极小模型（0.5B/1.5B）上下文窗口小、质量弱。
- 需要：本地引擎时降级策略（只带最近 1 轮 + 截断回答 ≤500 字；极小模型档禁用多轮或提示「本地多轮质量有限」）；
  `local_only=true` 时强制本地并禁用云端 fallback；成本/延迟提示。
- 影响：不处理会在本地档出现超窗、极慢或答非所问。

### G10 成本 / 限流 / 429 / 重试（缺失，中）

- 现状：真实网关未接；retry/429 映射只体现在 `provider_test`（S-17）；成本估算表存在（`resources/pricing.json:1-39`）但追问未计量。
- 需要：按真实 usage 计费并入 `usage_daily`；429 退避与错误气泡；重试不丢线程；多轮累计成本提示。
- 影响：多轮会把单次成本放大数倍（见 §4.3 估算），没有预算/展示容易失控。

### G11 隐私 / 脱敏（缺失，高）

- 现状：历史库刻意不存 OCR 原文（`capture.rs:115-122` 传 None；`history_repo.rs:6` 禁日志文本）；追问的选区/回答若入库是新隐私面。
- 需要：默认只在内存保留线程（关窗即清）；持久化需显式开关（跟 `history.enabled` 联动或新增 `history.saveAnswers`）+ 隐私说明更新；
  一键清空覆盖 messages；日志绝不打印选区/回答；云端发送前尊重 `privacy.allowTextUpload/localOnly`（当前命令层未门禁，见 `docs/实施架构.md:309`）。
- 影响：不做会在「历史即隐私」上踩线（项目 `PRIVACY.md`；`docs/概要设计说明书.md:584-585` 已明确「历史含文本内容需在隐私说明中说明、支持一键清空」）。

### G12 跨会话 / 历史恢复 / 长回答 / 离线（缺失，中）

- 现状：仅一个活动会话，新框选作废旧会话（`session.rs:164-180`）；无历史页；无离线多轮（骨架网关无所谓）。
- 需要（完整版）：历史对话列表 + 恢复（`result_reopen(sessionId)` 或新命令）；恢复后线程只读（不续聊或另开新会话）；
  长回答折叠/虚拟化；离线时仅本地模型可用且明确提示。
- 影响：属于体验完整性，不阻塞 MVP。

## 3 设计方案

### 3.1 目标与边界

**目标（MVP）**：在结果窗内，用户可对当前回答连续追问；旧回答保留为历史气泡；新回答流式追加；
上一轮 Q&A 进入模型上下文；重答/取消/关闭语义清晰；真实 IPC 可成功；有可复跑验收。

**非目标（MVP 明确不做）**：DB 持久化、历史对话恢复、跨会话继续追问、多窗口、图像追问、i18n、富文本/Markdown 渲染器重构。

**兼容性约束**：
- 契约「只增不改」（`docs/接口契约.md:584-585`），新增字段必须可选且有默认值；
- 命令名/参数名逐字实现（`:279`）；`IPC_CONTRACT_VERSION=1` 不递增（加可选字段属兼容变更，但需修订记录）；
- `history.enabled=false` 时不得写任何内容；日志禁文本（`:577`）；
- 骨架模式行为仍须确定性可复现（§12，`:495-513`）。

### 3.2 数据模型：两套方案与推荐

**方案 A（MVP，内存线程，无迁移）**

- 新增 `services/conversation.rs`：`Turn { task_id, parent_task_id, role, text, status, engine, usage, error_code, created_at }`；
  `TurnStore { HashMap<SessionId, Vec<Turn>> }` 挂在 `AppState`（`app/state.rs:28-55` 加字段）。
- 生命周期：`spawn` 时开始 assistant turn；`delta` 累积正文；`done/cancelled/error` 定稿；
  `result_close` / `begin_capture` / `capture_cancel` 清理；`history.enabled=false` 时也只走内存（本来就不落库）。
- 优点：0 迁移、0 隐私面变化、1–2 天可落地；Turn 结构与完整版 messages 表字段一一对应，可平滑演进。
- 缺点：关窗/新框选即丢；不能做历史恢复。

**方案 B（完整版，SQLite）**

- `messages` 表 + `tasks.parent_task_id`（§3.5）；写路径与 A 同一 `Turn` 结构；读路径供历史恢复；清理/隐私开关联动。
- 推荐：**A → B 渐进**。不要在 MVP 直接上 B，因为会同时引入迁移、隐私、清理、恢复四类风险，
  而多轮质量验证要等真实网关，优先级不匹配。

**不推荐方案 C**：独立 `conversations` 表 + `conversationId` 贯穿事件/命令。理由：当前产品一次框选 = 一个会话，
`SessionId` 已是天然作用域；引入第二套 id 会增加契约、历史、事件三处同步成本，收益为零（除非未来支持「同一对话多次框选」）。

```rust
// 1) 定位会话：不依赖 TaskStore（修复 F1）
let (session, selection, last_task) = {
    let store = state.session.lock();
    let current = store.current().ok_or_else(|| AppError::invalid_state("没有活动会话"))?;
    if store.current_phase() != SessionPhase::ShowingResult {
        return Err(AppError::invalid_state("仅结果展示阶段允许追问"));
    }
    let last = current.task_ids.last().cloned()
        .ok_or_else(|| AppError::invalid_state("会话没有可追问的任务"))?;
    if task != last {                       // 只允许对着最近一轮追问
        return Err(AppError::invalid_state("只能对最近一轮回答继续追问"));
    }
    (current.id.clone(), current.selection.clone()
        .ok_or_else(|| AppError::invalid_state("会话缺少选区"))?, last)
};

// 2) 组装上下文（MVP：仍单 prompt；context = 选区 + 最近 N 轮问答摘要）
let turns = state.turns.lock().recent(&session, MAX_TURNS);          // Vec<Turn>

let mut vars = HashMap::new();

vars.insert("context", context.as_str());
```

### 3.7 提示词改造

**MVP（不改模板，修语义）**：

- `{context}` = 选区原文（截断）+「\n\n【上一轮问答摘要】\nQ: …\nA: …」最近 1–3 轮；
- `{question}` = 本次追问；
- 截断规则：选区 ≤ `MAX_SELECTION_CHARS`（建议 2000 字）、单轮回答 ≤ 1500 字、总 context ≤ 6000 字；
- 这样 `followup.md` 的既有约束（不重复上一轮、更正前误、300 字内）首次真正生效；
- 需要在 `followup.md` 头注释里把 `{context}` 的描述改为「选区原文 + 上一轮问答摘要」并与实现对齐。

**完整版（多轮 messages）**：

```text
messages = [
  { role: "system",    content: followup.md 正文（去掉 {question}/{context} 插槽，改为纯系统约束） },
  { role: "user",      content: "【框选内容】\n{selection}\n\n【问题】\n{first_question}" },
  { role: "assistant", content: "{first_answer}" },
  ... 最近 N 轮 ...
  { role: "user",      content: "{followup_question}" }
]
```

- `followup.md` 改为 system prompt 模板（变量只保留 `{lang}`/`{mode}` 等可选），`PromptEngine::KNOWN_VARS`（`prompt_engine.rs:19-28`）
  与模板测试（`:210-244`）同步更新；用户覆盖机制（`%APPDATA%\SnipAsk\prompts\`，`prompt_engine.rs:114-134`）保持不变。
- 预算：`estimated = Σ chars * 0.6`（中文为主保守系数）；从最旧轮次裁剪；system + 选区 + 最近 1 轮不可裁；
  裁剪后在 `task:started` 上下文日志（不含正文）记录 `turns_kept/turns_dropped/est_tokens`，供诊断。

### 3.10 验收标准

**MVP（必须全过）**

1. **真实 IPC 可用**：首轮 done 后在真实 Tauri 中追问，`task_followup` 返回新 `TaskId`（非 SA-1099），
   事件序列 `task:started(parent=T1) → task:delta* → task:done`；UI 首轮回答仍然可见。
2. **连续 3 轮**：`parent` 链 T1→T2→T3 正确；UI 呈现 3 组 Q/A；同一时刻只有最后一条在流式（前一条文本冻结）。
3. **上下文注入**：fake gateway 捕获请求，断言包含上一轮回答正文（截断后）；`{context}` 不再只有选区文本。
4. **重答**：`menu_execute` 重答后线程被重置（parent=null → 单条新气泡），旧任务取消。
5. **取消**：追问中点取消 → 无后续该任务事件；部分回答保留并标记已取消；可继续追问。
6. **失败与重试**：注入网关错误（mock/fake gateway）→ 错误内联在该气泡；点击重试可再次发起同一追问（依赖 §3.9 修订）。
7. **并发**：流式中输入区禁用；若绕过 UI 直接调用，返回可读错误（建议新增 message「请等待当前生成结束」，仍用 SA-1099）。
8. **隐私**：`history.enabled=false` 时无任何内容落盘（MVP 内存模式天然满足）；日志无选区/回答文本。
9. **回归**：`cargo test`（新增至少 8 项：TurnStore、context 组装/裁剪、命令定位、parent 事件、状态机）、
   `cargo fmt --check`、`cargo clippy -- -D warnings`、`pnpm typecheck`、`pnpm build:web` 全绿。

**完整版追加**

10. 迁移：v1 旧库升级到 v2 后 `tasks`/`messages` 正常读写；重复启动幂等；`cleanup/clear` 覆盖 messages。
11. 历史恢复：可从历史打开某次会话并查看线程（只读）；恢复后「继续追问」要么禁用、要么新开会话（产品决策）。
12. 预算：5 轮追问下 `est_input_tokens ≤ 配置预算`，超预算时丢最旧轮并记录诊断字段；本地档自动降为 1 轮。
13. 隐私：`PRIVACY.md` 更新、一键清空覆盖 messages、脱敏规则（日志/错误 detail 不含正文）。
14. 成本：`usage_daily` 累计多轮真实 usage；结果窗显示本轮与累计费用。

## 5 结论

### 5.1 是否可行

**可行，且改动面可控。** 技术栈与现有架构天然支持：会话即对话作用域、结果窗是常驻单页、任务事件流已有 taskId 过滤、
提示词引擎支持用户覆盖、SQLite 仓储已有迁移雏形。风险主要不在技术难点，而在**现状的三处「名不副实」**（F1/F2/F3）与**真实网关依赖（F7）**。

### 5.2 是否已部分完成

**是，但完成的是「管道」不是「多轮」**：

- 已完成（可直接复用）：契约命令与状态约束、`TaskKind::Followup`、`resolve_followup`、命令骨架（会话/阶段校验）、
  `followup.md` 模板（质量可用）、`prompt_engine` 变量与覆盖机制、结果窗追问输入（Enter/Shift+Enter）、
  `task:*` 流式事件、取消机制、会话状态机对 `showingResult→executing` 的支持、mock 追问演示、历史库 sessions/tasks。
- 未完成（本需求核心）：真实 IPC 可用性（F1）、上一轮上下文注入（F2）、线程 UI（F3/F4）、
  parent/线程事件语义（F5）、失败重试（F6）、持久化/历史恢复（G8）、真实网关（G7）。

### 5.3 最短落地路径（推荐）

1. **P0 修 F1**（0.5 人日）：`task_followup` 改以当前会话 + `session.task_ids.last()` 定位；补 2 条单测。
2. **后端最小线程 + 上下文注入**（2.0–2.5 人日）：`TurnStore` + `task_runner` 正文累积 + `{context}` 拼接/截断 + `parent` 事件 + 契约/TS 同步。
3. **前端线程 UI**（3.0–3.5 人日）：`turns` 状态 + ThreadView + 事件路由 + 乐观气泡 + 流式禁用/取消/错误内联 + mock 同步。
4. **状态机/重试 + 隐私边界**（1.0–1.5 人日）：失败不改终局（或允许 error→executing）、重试按钮、动作白名单、日志脱敏。
5. **测试与联调**（1.5–2.0 人日）：Rust 单测 + fake gateway 捕获 prompt + 前端纯函数测试 + 真实 IPC 手动清单。
6. （并行）真实网关 3–5 人日；完成后补真实模型多轮质量/时延/成本验收。

**MVP 合计 ≈ 8.5–10.5 人日；若接受「失败需关闭重开」可压到 6.5–7.5 人日；完整版 +11–14 人日。**

### 5.4 「如果只能做最小版本」的建议

如果资源只允许一个最小可用版本，按下面这个顺序做，**不要先动 DB 与提示词模板**：

| 步骤 | 改动 | 人日 | 说明 |
| --- | --- | --- | --- |
| ① **修 F1（不可省）** | `action.rs::task_followup` 不再查 `TaskStore`，用当前会话 + `task_ids.last()` | 0.5 | 不修则功能 100% 不可用；这是「前置」不是「增强」 |
| ② **后端记住上一轮回答并注入** | `task_runner` sink 累积正文 → `AppState.last_answer: Mutex<HashMap<SessionId, Vec<(String,String)>>>`（或迷你 TurnStore）→ `task_followup` 把「选区 + 最近 1 轮问答」拼进 `{context}`（≤4000 字） | 1.0–1.5 | 模板不改，只修 `{context}` 语义；这是「多轮」与「单轮」的分水岭 |
| ③ **结果窗保留历史** | `ResultWindow` 用 `turns` 数组：追问时不再清空，把上一轮定稿、新轮追加；只流式最后一条；旧轮可折叠 | 1.5–2.0 | 若连 `parent` 字段也不想加，可用「本地按钮意图」判断，但重答/追问竞态会错挂气泡，建议顺手加 `parent`（+0.1 人日） |
| ④ 基础防呆 | 流式期间禁用输入；错误内联 + 保留输入可重试（后端失败态先按现状，用户可关闭重开） | 0.5 | 不加也能用，但体验差 |
| ⑤ 测试/验收 | Rust 4–6 条 + fake gateway prompt 断言 + 手动真实 IPC 清单 | 1.0–1.5 | 至少要能证明「上一轮回答进了 prompt」 |
| **合计** | | **≈ 4.5–6.0** | 不含真实网关；不做 DB 迁移、不改状态机、不做历史恢复 |

**最小版本的已知取舍（必须向用户/Lead 明示）**：
- 关窗/新框选即丢对话（内存）；
- 追问失败一次后需关闭重开（错误态终局）；
- 只带最近 1–2 轮上下文，长对话会「遗忘」更早内容；
- 骨架模式下看不到 prompt 效果（需 fake gateway 或真实网关）；
- mock 预览必须同步，否则仍会误判。
