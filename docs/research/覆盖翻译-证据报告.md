## 1 结论速览

| 问题 | 结论 | 关键证据 |
| --- | --- | --- |
| 覆盖翻译能不能做？ | **能**。在冻结帧上把 OCR 行框区域模糊 + 半透明遮罩，再在原位置绘制译文，视觉上等价于「原句被译文替换」 | 6 张真实截图（含 1 张真实窗口）原型全部跑通，见 §5 |
| 覆盖的是谁？ | **只能是框选 AI 自己的 overlay 画布**；不能修改目标应用（见 §4 C 方案、§8） | 架构：overlay 是独立窗口 + 冻结帧 `<img>` |
| 中→英在同一位置放得下吗？ | 同一字号下英文字符数是中文的 **2.46×**（P50），**行宽是 1.82×**（P50）→ 逐行原框「不换行」只有 **15.1%**，直接逐行覆盖 **42.7% 溢出** | 100 张语料 1373 个含中文行（§6.1/§6.3） |
| 段落合并有用吗？ | 有用。行→段合并把行数减少 **32.2%**（2288 行 → 1552 块），在**允许利用空白**的前提下，块级四档为 **原字号不换行 18.2% / 缩小字号 52.2% / 换行 29.6% / 溢出 0%**，字号中位只缩到 **0.80**；对照「逐行 + 允许空白」字号中位缩到 **0.61** | 100 张语料 1335 个含中文块（§6.2/§6.3） |
| 需要多复杂的版式算法？ | 5 档 + 空白扩展即可：`行合并 → 字号搜索 → 换行 → 吃空白 → 降级双语浮层`；100 张语料里 **53.5%** 的块靠吃空白才放下，**0%** 落到溢出 | §6.5 伪代码 |
| 触发时机与阶段机 | 菜单选「覆盖翻译」后进入 `translating → covered`；ESC 第一次回原文、第二次取消；可在覆盖层上放「原文/双语/重译/重新截屏」工具条 | §7.2 |
| 性能 | 渲染（100 块）在本机 Python 原型为 **821ms/86 块（≈9.5ms/块）**，生产 Canvas 预期 0.1–0.3s；翻译 100 行：云端批处理 **≈3–4.5s**（S-05 首字 P95 0.87s），本地 0.5B **40–80s（只适合 ≤20 行）** | §7.7 |
| 工作量 | **MVP ≈ 7.5 人日**，含真机加固 **≈10 人日**（拆解见 §7.8） | — |

**一句话**：**推荐方案 A（冻结帧覆盖层）**——当前 overlay 已经是「冻结帧 + 绝对定位层」结构，S-01 保证物理像素对齐 0.01px、S-02/S-03 保证 OCR 时延与缓存路径、S-15 保证准确率；覆盖翻译只是在 frame 之上再加一层「模糊 + 译文」画布，不需要跨进程写别人窗口，也不需要逐帧跟随屏幕。

## 3 环境与方法

### 3.1 语料与输入

- **100 张真实渲染截图**：`.verify/spikes/S-11-S-15/corpus/real/`（web/chat/doc/code/dark × 20），物理尺寸 2560x1440 / 2880x1620 / 3440x1440（视口不同），带真值（S-15 用它测过准确率）。
- **1 张真实 Win32 窗口截图**：用仓库的 DPI 感知 BitBlt 工具抓 Windows 11 记事本窗口（`scripts/spikes/tools/screenshot.ps1 -X 100 -Y 100 -W 1000 -H 800`），裁到 948x790 后作为第 6 张原型输入（含标题栏/菜单/状态栏等真实 chrome）。**这张图证明原型对「非渲染器产生的真实窗口位图」同样成立**（ClearType 边缘、真实 DPI 缩放、窗口边框）。

### 3.2 OCR 口径（与生产一致）

```
原生帧 (W×H)
  ├─ det：整屏缩放（长边≤3200 且像素≤3.0 Mpx，绝不放大）→ PP-OCRv4 det → 框 ×1/scale 回原生
  └─ rec：对**原生裁框**做 PP-OCRv4 rec（batch 6，无 cls）→ 置信度 <0.6 丢弃，高度 <6px 丢弃
```
> 与 S-02/S-03 落地口径一致（`det_input_size` 双约束 + 整屏 det 缓存）。差别是：本报告的原型为了「整屏覆盖」把**所有**框都 rec 了，所以 rec 耗时明显高于 S-03 选区口径（见 §7.7 性能预算说明）。

实测（100 张，每张整屏）：

| 量 | P50 | P95 | max | 说明 |
| --- | --- | --- | --- | --- |
| det（3.0 Mpx 输入） | 751ms | 975ms | 1488ms | 与 S-02 复核值 724/743ms 同量级（本窗口有别的成员并行负载） |
| rec（原生化，全部框） | 1078ms | 2975ms | 4386ms | 代码页 43–59 行最慢；**生产只对选区内框 rec**，不能直接套用 |
| det+rec 合计 | 1851ms | 3821ms | 5016ms | 每张图平均 22.9 行 |

### 3.3 译文来源（质量声明）

- 引擎：`llama-server.exe`（llama.cpp CPU 构建，`-ngl 0`）+ `qwen2.5-0.5b-instruct-q4_k_m.gguf`。
- 提示词：「专业中→英翻译，只输出一行英文译文」；含中文比例 <15% 的纯英文/代码行**原样保留、不覆盖**（产品规则）。
- **质量一般**：实测 26 次请求平均 **581ms/请求**（30–60 字段落）；个别专名/歌名会错（如「海底·一支榴莲」→ `A banana·fruit`），OCR 残缺字符会被翻成 `□□□`。因此**只看版式，不看翻译质量**。
- 译文全部落盘缓存 `data/translations_cache.json`（95 条），`proto_render.py` 复跑时**不需要模型**。

### 3.4 版式算法参数（原型实现值）

| 参数 | 值 | 说明 |
| --- | --- | --- |
| 行→段合并 | 垂直间距 ≤ **0.55×行高**；左边缘差 ≤ **0.9×行高** 或横向重叠 ≥ **50%**；行高比 0.7–1.45；单段 ≤ **6 行** | `overlay_lib.merge_lines` |
| 字号搜索 | 源行高 × {1.00, 0.95, …, **0.60**}（5% 步长），最小 8px | 5 档见 §6.5 |
| 译文行高 | **1.20 × 字号** | 英文 UI 正文常见 1.2 |
| 换行 | 贪心按词；超长单词按字符硬切 | 无断词表（产品可加 hyphenation） |
| 空白扩展 | 横向 ≤ min(右侧空白, **0.6×块宽**, **320px**)；纵向 ≤ min(上下空白, **1.8×块高**)，留 3px 不压邻居；渲染时自上而下、允许冲突回退（先禁向上扩展、再不扩展） | §6.5 |
| 覆盖层渲染 | 高斯模糊 σ = clamp(**0.38×源行高**, 1.8)；ksize = 4σ+1；**半透明遮罩 flatten α=0.5**（向局部背景色收敛）；外扩 pad = **0.14×行高**（≥2px，上边只留 2px） | 实测 σ P50 **8.1–10.3px** |
| 文字颜色 | 背景亮度 <0.45 → 浅字 `#F5F7FA`；否则深字 `#11151A`；对比度 <4.5:1 时加 scrim（0.35–0.45 α） | WCAG 对比度 |
| 描边 | 1px、同色反色、α=46/255（模拟 `text-shadow`） | 保证模糊背景可读 |

### 3.5 复跑命令

```powershell
# 全部命令在仓库根目录执行；PYTHONIOENCODING 只影响控制台中文显示
$env:PYTHONIOENCODING = 'utf-8'
$py  = '.verify/venv-ocr/Scripts/python.exe'
$scr = '.verify/research/overlay/scripts'

# 1) 100 张语料 OCR（整屏 det 预算口径 + 原生 rec），写 data/ocr/*.json（约 3.5 分钟，可缓存续跑）
& $py "$scr/ocr_corpus.py"

# 2) 30 行真实译文校准（字符/宽度扩张比 + 回归），写 data/translation_sample.json
#    需要 llama-server（默认 http://127.0.0.1:8796，可用 OVERLAY_TRANSLATE_URL 覆盖）
$llama = "$env:USERPROFILE\.lmstudio\extensions\backends\llama.cpp-win-x86_64-avx2-2.28.2\llama-server.exe"
$model = '.verify/spikes/S-05-S-06/artifacts/qwen2.5-0.5b-instruct-q4_k_m.gguf'
Start-Process $llama -ArgumentList @('-m',$model,'--host','127.0.0.1','--port','8796','-c','1024','-np','1','-t','6','-ngl','0','--no-warmup') -WindowStyle Hidden
& $py "$scr/calibrate_translate.py"

# 3) 预热原型译文（自管进程 + 自动重启 + 增量缓存；模型被外部 kill 也能续跑）
& $py "$scr/warm_translations.py"

# 4) 渲染 6 张原型 before/after/boxes/compare（离线，只读译文缓存）
& $py "$scr/proto_render.py"
#    也可只跑指定图：--images web_00 chat_03

# 5) 100 张语料版面量化（离线；伪英文按校准长度生成，只评版式）
& $py "$scr/metrics_layout.py"

# 6)（可选）真实窗口截图 → 单图 OCR
powershell -ExecutionPolicy Bypass -File scripts/spikes/tools/screenshot.ps1 `
  -Out .verify/research/overlay/data/real_notepad_full.png -X 100 -Y 100 -W 1000 -H 800
& $py "$scr/ocr_one.py" --image .verify/research/overlay/data/real_notepad_src.png --id real_notepad --category realcapture
```

## 4 方案对比（必须明确推荐）

| 维度 | **A. 冻结帧覆盖层（推荐）** | B. 实时穿透悬浮窗 | C. 直接改写目标应用文本 |
| --- | --- | --- | --- |
| 原理 | 截图后 overlay 显示冻结帧 `<img>`，在其上按 OCR 框模糊 + 画译文；画面静止 | 透明 click-through 悬浮窗跟随屏幕，逐帧抓屏 + OCR + 重绘 | 通过 UI Automation/MSAA/注入/无障碍接口改目标应用控件文本 |
| 可行性 | **高**：当前架构已具备（frame dataUrl、boxes、绝对定位层） | 中低：需持续抓屏（WGC）、逐帧 OCR（每帧 ~0.7–3.8s，本报告实测），且悬浮窗无法可靠拿到「此刻屏幕」（自身也会被截进去，需排除自己） | **不可行**：跨进程无通用写入通道。控件文本大多不可写（只读 UIA 值、自绘 UI、Canvas/WebGL/游戏/终端），写回会破坏布局、触发应用状态机、违反完整性级别与 UIPI；等于注入 + 伪造用户输入，安全和合规都不可接受 |
| 时延 | 一次性：帧就绪后 OCR（S-03 缓存路径 P95 **596ms**）+ 翻译（云端首字 P95 **0.87s**）+ 首屏渲染（100 块目标 **<0.3s**） | 每帧都要重跑「截屏+OCR+翻译+渲染」；滚动 60fps 下完全跟不上（OCR 是百毫秒级）；需降帧到 1–2fps 且译文滞后 | 不需要翻译渲染时延，但写入成功率≈0 |
| 对齐精度 | **高**：S-01 实测混合 DPI 双屏端到端 **0.01px**；OCR 框即覆盖框，1:1 物理像素 | 依赖抓屏/窗口层级/时间差，滚动时错位、动画时抖动 | 无意义（改的是目标应用自己的排版） |
| 滚动/视频 | **不支持跟随**（冻结帧不变）；产品语义是「框选一次、看一次」，提供「重新截屏」按钮即可 | 理论支持跟随，但需逐帧同步；视频/动画下译文闪烁、错位，CPU 完全不够（本机整屏 det P95 975ms/帧） | 视频/自绘内容根本拿不到文本 |
| 隐私 | 帧只在本地内存，OCR 本地（S-15 证明本地准确率 99.29%）；可选仅选区 OCR/翻译 | 必须**持续**抓整屏，隐私面更大（每一屏内容都可能被处理） | 需读取目标应用完整 UI 树，范围更大 |
| DRM/全屏独占 | 受 S-09 约束：受保护面截图**纯黑** → 没有可模糊的帧，只能 `SA-1001` 降级提示；`WDA_EXCLUDEFROMCAPTURE` 窗口截不到 → 无内容可覆盖 | 同样受 DRM 约束（抓屏同样是黑的），而且悬浮窗在全屏独占（exclusive fullscreen）下可能根本不可见 | 与 DRM 无关，但同样不可行 |
| 多屏混合 DPI | 沿用 S-01：统一 dpr（= overlay WebView 实际 devicePixelRatio，本机 1.5），物理 px ↔ CSS px 纯换算；副屏 UI 观感偏小属已知遗留 | 需要处理「窗口跨屏 + 每屏各异缩放 + 顶置层级」，比 A 复杂得多 | — |
| 实现复杂度 | **中低**：新增 1 个 canvas 层 + 1 个 worker 版式模块 + 契约阶段 2 个状态 | 高：持续抓屏管线、帧同步、悬浮窗穿透与层级、性能降级策略 | 极高且不可维护 |
| 结论 | **推荐（MVP 唯一方案）** | 不做；仅作为「后续增强：滚动跟随」的远期探索（需要 1–2fps 的整屏 OCR 预算，与 S-02 现有的 1.2s 阈值冲突） | **明确不做** |

**推荐理由（一句话）**：覆盖翻译的语义本来就是「把这一屏截图里的文字替换掉给用户看」，冻结帧天然就是正确的坐标基准和隐私边界；实时跟随只会把「一次 OCR + 一次翻译」变成「每帧 OCR + 每帧翻译」，在本机实测下完全不可行。

## 6 版面量化（100 张语料，真实 OCR + 校准译文长度）

> 方法：真实 OCR 行框 → 行合并成段 → 用**校准回归**把「中文字符数」外推成「英文非空白字符数」→ 用**等长伪英文**（常用词、平均词长接近真实英文）代替译文 → 用**同一套真实版式算法**测四档。伪英文只影响断行位置，不影响长度分布；真实译文版式见 §5。
> 校准来源：30 行分层抽样真实译文（web/chat/doc/code/dark 各 6 行）。

### 6.1 中→英长度扩张比

| 量 | mean | P50 | P95 | max | min |
| --- | --- | --- | --- | --- | --- |
| **字符扩张比**（英文字符数 / 中文字符数） | **2.49** | **2.46** | 3.59 | 4.24 | 1.00 |
| **单行宽度扩张比**（同字号英文行宽 / 源行框宽） | **1.77** | **1.82** | 2.62 | 2.93 | 0.73 |
| 每字符前进宽度 k（× 源行高） | 0.523 | **0.518** | 0.583 | 0.587 | 0.469 |

回归（用于 100 张语料外推）：`eng_chars ≈ 3.437 × cjk_chars − 1.910`（**R²=0.774**，残差 σ=12.6 字符；短句误差大，长句更稳）。

按类别（P50）：

| 类别 | 字符扩张比 | 宽度扩张比 | 说明 |
| --- | --- | --- | --- |
| web | 2.46 | 1.55 | 结构性短标签多 |
| chat | 2.49 | 2.04 | 气泡窄，扩张压力最大之一 |
| doc | 2.04 | 1.53 | 长句占比高，逐字比低但整行宽 |
| code | 2.62 | 1.80 | 中英混排，中文注释短 |

### 6.5 推荐自适应算法（伪代码）

```text
输入：选区内 OCR 行框 lines[]（物理 px，来自 selection_commit.boxes 或整屏 det 缓存过滤）
     译文 translations[]（按块，异步/流式返回）
     帧尺寸 (W,H)

# ① 行合并成段（回收短行浪费的横向空间）
blocks = merge(lines):
  按 (y, x) 排序；贪心把满足以下条件的行并入当前段：
    -0.3h ≤ 下一行.y0 - 末行.y1 ≤ 0.55h          # 同一段的行距
    |下一行.x0 - 末行.x0| ≤ 0.9h 或 横向重叠 ≥ 50%  # 同列/同缩进
    0.7 ≤ 行高比 ≤ 1.45                          # 同字号
    段内行数 ≤ 6
  段文本 = 各行文本按行拼接（中文加空格，英文/代码保留原样）

# ② 每段求版式（五档，先不给空白，再吃空白）
for block in blocks:
    avail_w, avail_h = block.w, block.h          # 第一轮：真实「原框容纳率」
    hit = fit(block, text, avail_w, avail_h)
    if hit == null:                              # 第二轮：吃已知空白
        avail_w += min(right_gap(block), 0.6*block.w, 320)
        avail_h += min(down_gap(block)+up_gap(block), 1.8*block.h)
        hit = fit(block, text, avail_w, avail_h)
    if hit == null:                              # 第三轮：降级
        hit = degrade(block, text)               # 最小字号 + 截断 → UI 改双语浮层/放大气泡

fit(block, text, avail_w, avail_h) -> Fit | null:
    base = median(行高)                          # 源字号（物理 px）
    min_px = max(12, 0.60*base)                  # ★ 可读性下限（见 §6.6）
    for size in base*(1.00, 0.95, ..., 0.60):
        if wrap_text(text, size, avail_w).lines == 1 and width(text,size) ≤ avail_w:
            return tier1(size, 1 行)             # 原字号不换行
        if 2 ≤ lines ≤ min(3, avail_h/(1.2*size)) and 总高 ≤ avail_h:
            return tier2(size, lines)            # 换行（原字号优先）
    # 若上面的 size 循环里先命中「1 行」但字号已 <0.95base → tier3 缩小字号
    return null

# ③ 冲突消解（渲染顺序自上而下，避免后画的覆盖层糊掉先画的译文）
for block in blocks 按 y 升序:
    if cover(block) 与任何已放置 cover 相交:
        block = relayout(block, allow_expand_up=false)   # 先禁向上扩展
        if 仍相交: block = relayout(block, allow_expand=false)  # 再完全不吃空白
    place(block)

# ④ 渲染（Canvas 一层：先糊后字）
for block in blocks:
    σ = clamp(0.38 * 源行高, ≥1.8)               # 模糊半径（物理 px）
    patch = gaussian_blur(frame[cover], σ)        # 或用 ctx.filter='blur(σpx)'
    patch = mix(patch, median(patch), 0.5)        # 半透明遮罩，去掉「灰糊块」
    draw(patch)
    text_color = luminance(patch) < 0.45 ? #F5F7FA : #11151A
    if contrast(text_color, patch) < 4.5: 加 scrim(0.35–0.45)
    draw_text(block, lines, size, 行高=1.2*size, 左对齐, 1px text-shadow)
```

**预期指标（按本报告实测）**

| 指标 | 预期 |
| --- | --- |
| 段块四档（100 张语料） | 原字号 18.2% / 缩小 52.2% / 换行 29.6% / 溢出 0% |
| 字号中位（相对源字号） | 0.80（下限 0.60，P10=0.60，触发下限的块 ≈0.9%） |
| 需要「溢出让位」的块 | <1%（真实译文原型 1.2%，因为真译文比回归预测更长/更短） |
| 需降级为双语浮层的小控件 | ≈6.7%（字号 <14px 的块；含 <12px 的 0.9% 必须降级） |
| 覆盖块平均渲染耗时 | <3ms/块（Canvas），100 块 <0.3s，可流式逐块出图 |

### 6.6 可读性下限（重要工程约束）

- 当前算法允许缩到 **0.60×源行高**（原型代码里下限取 `max(8, 0.6×源行高)`）。在本机语料（截图按 1:1 物理像素，正文源行高 18.8–22.2px）下，最终字号落点：P10=14px、P50=21px，**<12px 的块占 0.9%**、<14px 占 6.7%、<16px 占 17.2%。
- 真实 overlay 的 dpr=1.5（本机），即 **物理 px = 1.5 × CSS px**；浏览器最小可读正文字号建议 ≥11 CSS px ⇒ **物理下限 16.5px**。
- 结论：实现时必须把 `min_px` 从「0.60×源行高」改成 `max(0.60×源行高, 11×dpr)`；因此部分块会从「缩小字号」升级为「换行」或「降级气泡」。原型数据里 **6.7% 的块（<14px）需要走降级/换行路径**，与 §6.3 的 0% 溢出并不矛盾——降级是本报告推荐的 UI 兜底（双语浮层/放大气泡），不是渲染失败。


**新增命令/事件**（契约 v2，需 Lead 统一评审）：
- `translate_overlay`（或复用 `menu_execute` 的 `action:"translate"` + `mode:"cover"`，推荐后者，避免新增命令）：参数 `{session, action:"translate", mode:"cover"}`；返回 `{taskId}`（沿用 task:* 流式事件）。
- 事件 `translate:progress { session, blocks: [{key, dstText}] }`（分批，每批 8–10 块；可复用到已知的 `task:delta` 机制）。
- 事件 `translate:ready { session, lang, blocks: [{key, srcText?, dstText}], total, dropped }`。
- 命令 `translate_overlay_cancel { session }`：取消进行中的翻译（复用 `task_cancel`）。
- 原文/双语切换**纯前端**（不需要 IPC）：译文与 OCR 原文都在前端内存里；切「原文」= 隐藏 canvas 层（`display:none`，帧仍在），切「双语」= 覆盖层下移 15% 或文字用双语两行/气泡。

**触发时机**：`phase === "menu"` 且用户点「翻译（覆盖）」→ 前端直接进 `translating`（先渲染骨架：每个块的模糊补丁先出，译文后到；译文按批返回逐块填充）→ 全批到达后 `covered`。失败/超时回 `menu` 并复用现有 `overlay-error` 展示（`role="alert"` 已有）。

### 7.3 数据流、缓存、分批

```text
selection_commit ──► SelectionResult.boxes（绝对物理 px，已含选区过滤）
                       │
                       ├─(前端) 行合并 + 版式预求解（blocking 产物，worker 内完成，<5ms）
                       │
menu_execute(translate, mode=cover)
                       │
                       ▼ 后端
              按块取译文：
                · 译文缓存键 = sha1(normalize(srcText) + targetLang + modelId + promptVersion)
                · 命中 → 立即返回；未命中 → 按「8–10 块/请求」批量调用 provider
                · 流式/分批发 translate:progress；每批到达前端就重排该块并绘制
                · 全部块完成 → translate:ready；取消 → task_cancel（批次间检查点）
                       │
                       ▼ 前端
             TranslationOverlay：逐块 drawImage(模糊补丁) + fillText(译文)
             原文切换 = 隐藏 canvas；重译 = 清空该 session 的译文缓存重跑
```

- **缓存**：进程内 LRU（按 `session` 生命周期 + 跨会话短 TTL）+ 磁盘可选（S-13 本地模型场景）。同一屏重复框选 0 成本。
- **重排（re-layout）只在译文到达/字号策略变化时发生**，不做逐帧重排。
- 译文长度可能超出回归预测（模型啰嗦）→ **以真实译文重新跑一遍 `fit()`**，而不是信任预估；预估只用于「预占位」防跳动。

### 7.4 重新截屏与滚动

- 冻结帧语义下**不跟随滚动**：用户滚动目标应用后，overlay 上的画面仍是旧帧 → 工具条常驻「重新截屏」，点击 = `capture_freeze`（新 session，旧译文缓存按 session 作废，S-01 的窗口几何对齐逻辑自动复用）。
- 可选增强：监听鼠标滚轮（overlay 是顶层窗口，能收到滚轮）→ 提示「内容已变化，按 R 重新截屏」；不做自动逐帧跟随（理由见 §4 B）。
- 局部重截屏（只刷新选区）可作为后续增强：把 frame 裁到选区再重新 OCR/翻译，减少整屏开销。

### 7.5 多屏 / DPI

- **只用 overlay 实际 dpr**（S-01 结论：单个跨屏 overlay 只有一个 WebView 缩放比，本机 1.5；逐屏混用会让副屏偏移数百 px）。
- 本报告所有坐标/字号/模糊半径都是**物理 px**；渲染时用现有 `toCssRect` / `toCssPoint` 换算成 CSS px 再绘制（Canvas 用 `ctx.setTransform(1/dpr,0,0,1/dpr,...)` 或直接按物理 px 建 canvas、CSS 尺寸 = 物理/dpr）。
- 字号下限按 **11 CSS px × dpr** 物理 px 计算（本机 16.5px）。
- 已知遗留（S-01 §6.3）：统一 dpr=1.5 时，100% 副屏上的 overlay UI 观感偏小；覆盖层的译文也会同样偏小——若产品要求各屏一致，需要「每显示器一个 overlay」或按屏分片，属 UX 增强，不影响坐标正确性。
- 死区（外接矩形内无显示器区域）不应参与框选/覆盖；沿用 `rect_contains` 校验。

### 7.6 字体、深色模式、对比度、可访问性

| 项 | 决策 |
| --- | --- |
| 字体 | 英文 `Segoe UI`（Windows 默认 UI 字体，原型实测宽度稳定）；中文（双语模式）`Microsoft YaHei`；数字/代码可 `Cascadia Mono`。字体加载失败回退 `system-ui, sans-serif` |
| 字号 | 物理 px = `clamp(源字号×[0.6..1.0], 11×dpr, 源字号)`；行高 1.2 |
| 深色模式 | **不依赖主题变量**：按覆盖区域背景亮度（σ 模糊 + flatten 后的中位亮度）逐块决定文字色（<0.45 → `#F5F7FA`，否则 `#11151A`），再校验 WCAG 对比度 ≥4.5:1，不足则加 scrim。原型 6 张图对比度 min 6.35:1、无 scrim 触发 |
| 高亮/配色 | 覆盖底色来自「模糊后中位色」，不引入品牌色；溢出/降级块可加 2px 强调边（提示「这里是气泡译文」） |
| 可访问性 | ① OCR 原文保留在 DOM（`aria-label` 或视觉隐藏的 `<span>`），读屏可读原文+译文；②「原文/双语/覆盖」三态可键盘切换（`O`/`B`/`Esc`）；③ Esc 第一次回原文，第二次关闭（避免误退出丢失结果）；④ 最小字号 ≥11 CSS px；⑤ 不做纯色闪烁动画，尊重 `prefers-reduced-motion` |
| 内容保真 | 原文永不丢弃（内存中 `srcText`），任何时刻可恢复；覆盖层是「视觉替换」，不是数据替换 |

**预算结论（MVP 验收线）**：
1. 首块可见（骨架 + 首批译文）：**≤1.5s**（菜单点击 → 第一块有英文；与 S-05 首字口径一致）。
2. 全部 100 块覆盖完成：**≤6s**（云端）；本地 0.5B 明确**不承诺**（>40s，UI 需进度 + 可取消）。
3. 交互（切原文/双语）**≤1 帧**（只切 canvas 可见性，不重排）。
4. 100 块渲染峰值内存：<10MB（canvas 与帧同尺寸 RGBA，3640x1920 约 28MB 单张；用离屏缓存 1 张即可，不要每块新建 canvas）。

## 8 结论与边界

### 8.1 能做到什么程度（明确）

1. **能把选区内的中文文字区域「视觉上替换」成英文**：模糊 + 半透明遮罩（原文不可读）+ 原位置译文，字号/换行/空白利用自适应；6 张真实截图（含真实 Win32 窗口）均已跑通。
2. **覆盖只发生在框选 AI 自己的 overlay 窗口画布上**：冻结帧 `<img>` 之上再叠一层 canvas，**不改动目标应用的任何内容、不注入、不伪造输入**。用户关掉 overlay 即完全恢复。
3. **随时可恢复原文**：原文与译文都在前端内存，一键切回（视觉上隐藏覆盖层）；也可切「双语」（原文 + 译文同屏）。
4. **坐标可信**：物理像素口径 + S-01 的 0.01px 对齐；多屏统一 dpr，不做逐屏 dpr。
5. **网络/模型不可用时降级**：翻译失败 → 回菜单 + 错误提示（复用 `overlay-error`，`SA-1001` 等），不崩溃；本地模型仅作离线兜底且明确「慢/质量一般」。

### 8.2 不可行 / 受限边界（必须写清）

| 边界 | 说明 |
| --- | --- |
| **不能修改目标应用** | 覆盖只是「蒙一层画」；目标应用的滚动、输入、内容不受影响。任何「真的把别人的界面文字改掉」的方案（方案 C）都不可行且不合规。 |
| **DRM / 受保护内容** | S-09 实测：`WDA_MONITOR(0x01)`/DRM 受保护面 BitBlt+PrintWindow+WGC **全黑**；`WDA_EXCLUDEFROMCAPTURE(0x11)` 窗口从截图消失、WGC 也拿不到帧。→ **没有可用的冻结帧就没有覆盖**：只能按 `SA-1001` 提示「该窗口受保护，无法截图」，而不是假装覆盖成功。 |
| **全屏独占** | 全屏独占游戏/播放器下 overlay 可能不可见（顶层窗口被独占交换链遮挡）；S-09 已列入遗留（未在真机全屏独占下验证）。建议文档说明 + 提供「窗口化/无边框」建议。 |
| **滚动与视频不跟随** | 冻结帧是静态的，滚动后必须重新截屏（工具条按钮/R 键）。实时逐帧跟随（方案 B）在本机 CPU 实测下不可行（整屏 det P95 975ms/帧 + 翻译百毫秒~秒级）。 |
| **混合 DPI 副屏观感** | 统一 dpr=1.5 时，100% 副屏上的覆盖层文字会显小（S-01 §6.3 遗留）；坐标正确但 UX 需后续「每屏一个 overlay」增强。 |
| **OCR 错行/漏行** | S-15 字符准确率 99.29–99.38%，但代码行号列、`×`→`x`、`L`→`l` 等仍有错；OCR 框错位会导致译文错位/漏译。→ 覆盖前用置信度 + 高度 + 面积过滤（S-11 阈值），错块回退原文。 |
| **译文长度不可控** | 模型可能啰嗦（比回归预测长 30%+）→ 必须用**真实译文**再跑一遍 fit，并把溢出降级为双语浮层/放大气泡（原型实测溢出 1.2%）。 |
| **隐私面扩大** | 覆盖翻译天然是「整片区域 OCR + 外发翻译」；建议配置为「默认仅选区、整屏覆盖需显式开启」，并在首次使用时提示会外发选区文本（S-07 受限模式/隐私声明联动）。 |
| **模型质量** | 0.5B 只用于版式验证；生产按 S-05 结论用云端（关 thinking、流式）或本地 1.5B（慢路径）。译文质量需在产品里标注来源与「机翻」属性。 |

### 8.3 MVP 与后续增强

**MVP（≈7.5 人日）**
1. 选区覆盖：`menu_execute(translate, mode=cover)` → 段块级覆盖 + 原文切换 + 溢出降级气泡提示。
2. 云端翻译（S-05 口径：关 thinking、流式、首字 ≤1.5s），8–10 块/请求批处理 + 译文缓存。
3. Canvas 渲染 + Worker 版式；字号下限 11 CSS px；深色自适应；keyboard（Esc/O/B）。
4. 重新截屏按钮；错误回退菜单；S-01 坐标回归。

**后续增强（按价值排序）**
1. **双语对照模式**：覆盖层下移/半透明，原文与译文同时可读（适合学习/校对场景）。
2. **流式逐块覆盖**：首批译文先出图，剩余块渐入（把 100 块等待时间从 4s 拆成「0.9s 见首块」）。
3. **小控件专用气泡**：宽 <3×行高的短标签走「放大气泡/侧边浮层」，避免折行压邻居（原型页签问题）。
4. **整屏覆盖**：把「选区内框」放宽到「整屏 det 缓存过滤」，需要按 S-02 预算约束（整屏 100+ 行 rec 成本高，需分块/降采样）。
5. **本地模型档位**：S-13 的 1.5B/0.5B 离线兜底（≤20 行、流式、明确慢）。
6. **滚动跟随研究**（方案 B 的有限形态）：只在用户静止 300ms 后重截屏一次，仍需重跑 OCR+翻译，不承诺 60fps。

## 9 风险与处置（表格）

| 风险 | 影响 | 等级 | 处置 |
| --- | --- | --- | --- |
