# 框选 AI · 技术验证清单（Spike）

> 来源：《可行性研究报告》§0「Go 的前提条件（技术验证阶段必须确认）」与 §3.4「技术难点与应对」。
> 本清单把结论性描述转为**可执行、可判定**的 spike 任务：每条给出验证方法/工具、验收阈值、
> 负责人与状态。所有条目在脚手架阶段状态均为 **TODO**；完成后填写结论并更新状态为 DONE / FAILED。
>
> 执行约定：
> - 验证在任何正式代码合入前完成，脚本/样例放在 `scripts/` 或临时 `.verify/`（已 gitignore）；
> - 每项至少在两套环境各跑一次：**1080p 单屏** 与 **4K + 1080p 混合 DPI 双屏**；
> - 记录必须包含：日期、机器配置、Windows 版本、构建 commit、原始数据/截图、结论；
> - 任一「Go 前提条件」条目 FAILED 时，需回到技术方案（见报告 §3.2/§3.4）重新选型，不得直接进入 MVP。
>
> **P0 首轮 Spike（2026-11-04 ~ 11-05，结论已由下方 phase 2 处置更新）**：S-01 / S-02 / S-04 / S-07 / S-08 = **DONE**；
> S-03 原 det+rec 口径 968ms 未达标（缓存 rec-only 口径 596ms 达标）；S-05 本地 1.8B CPU 不达标、云端无 Key；S-06 无 Key。
> 逐项证据与原始数据索引见 [`docs/spikes/`](spikes/README.md)；复跑脚本见 [`scripts/spikes/`](../scripts/spikes/README.md)。
> 本轮验证环境：Windows 11 26200 / i7-12650H / 15.78 GiB；混合 DPI 双屏 2560×1440@150% + 1080×1920@100%
> （虚拟桌面物理矩形 (-1080,-470) 3640×1920；4K/200% 与单屏 1080p 真机未覆盖，见各记录「遗留」）。

> **P0 第二轮 · 门禁处置落地（phase 2，2026-11-05）**：按用户决策完成 4 项落地：
> ① **S-03 口径变更并落地**：选区 OCR 改为「整屏 det 缓存 → 选区过滤 + rec-only」（该口径 P95 596ms 达标；原 det+rec 口径 968ms 保留为对照），
> 实现于 `services/ocr_service.rs::OcrPipeline` 并接入 `capture/selection`；
> ② **S-02 像素预算落地**：det 改为「长边 ≤3200 且像素 ≤3.0Mpx」双约束（单 4K P95 1682ms → 794ms，双 4K 743ms，实测见 S-02/S-03 记录 §14）；
> ③ **引导页三档 AI 服务**：云端 / 极小模型（Qwen2.5-0.5B Q4 + 精简提示词，P95 3.2s、0.55GiB）/ 普通模型（HY-MT1.5-1.8B，质量优先但 CPU 慢），
> 三档均给出实测性能与隐私/成本提示；
> ④ **S-05 云端实测（用户提供 DeepSeek Key）**：`deepseek-flash` 关闭 thinking 时首字 P50 0.61s / P95 0.87s（达标），默认 thinking 首字 P95 4.59s（不达标，
> 真实网关必须显式关闭思考）；S-06 视觉腿可用（deepseek-flash 支持图片），**仅缺检索 Key**。
> 另：模型清单新增极小模型条目（第 4 条，size/sha256 已核验）；`provider_test` 真实连通性测试（S-17 预置）已落地。

## 4 验证记录模板

每个 spike 完成后在 Issue/PR 或 `docs/` 下附件中记录：

```text
编号：S-0x
结论：DONE / FAILED / BLOCKED
日期：YYYY-MM-DD
环境：Windows 版本 / CPU / 内存 / 显卡 / 屏幕（分辨率 + 缩放 + 数量）/ 构建 commit
步骤：1) ... 2) ... 3) ...
原始数据：耗时打点（P50/P95/max）、截图或录屏、日志片段（脱敏）
结果：是否达到验收阈值；未达标项的具体数值
处置：达标 → 记录到实施架构「实现边界」；未达标 → 调整方案（选型/降采样/降级）并重验
遗留：后续跟进项与负责人
```

## 5 维护说明

- 新增待验证能力时先加一行任务（编号顺延），再在实现前跑通；
- 结论变更（DONE → FAILED）必须回写本表并在 `CHANGELOG.md` 说明影响；
- 本表阈值与报告 §2.3/§7.2 保持一致，修改阈值需同步更新 README「验收与性能目标」；
- 每条 DONE/FAILED/BLOCKED 必须在 `docs/spikes/` 有对应记录并在本表「状态」列链接，原始数据放 `.verify/spikes/<编号>/`（gitignored）；
- P0 条目 FAILED/BLOCKED 时，先完成技术方案决策（选型/口径/阈值）再重新 spike，不得跳过门禁进入 MVP。
