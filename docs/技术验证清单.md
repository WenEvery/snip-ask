> 来源：《可行性研究报告》§0「Go 的前提条件（技术验证阶段必须确认）」与 §3.4「技术难点与应对」。
> 本清单把结论性描述转为**可执行、可判定**的 spike 任务：每条给出验证方法/工具、验收阈值、
> 负责人与状态。所有条目在脚手架阶段状态均为 **TODO**；完成后填写结论并更新状态为 DONE / FAILED。

> 执行约定：
> - 验证在任何正式代码合入前完成，脚本/样例放在 `scripts/` 或临时 `.verify/`（已 gitignore）；
> - 每项至少在两套环境各跑一次：**1080p 单屏** 与 **4K + 1080p 混合 DPI 双屏**；
> - 记录必须包含：日期、机器配置、Windows 版本、构建 commit、原始数据/截图、结论；
> - 任一「Go 前提条件」条目 FAILED 时，需回到技术方案（见报告 §3.2/§3.4）重新选型，不得直接进入 MVP。

| OCR 版面还原 | S-15（P1 后续 PP-Structure） | 表格/公式结构，P2 公式模型 |
| 网络与额度 | S-07、S-17 | 离线 OCR 可用、明确错误、云端/本地互为兜底 |

## 4 验证记录模板

每个 spike 完成后在 Issue/PR 或 `docs/` 下附件中记录：

```text
编号：S-0x
结论：DONE / FAILED / BLOCKED
日期：YYYY-MM-DD
环境：Windows 版本 / CPU / 内存 / 显卡 / 屏幕（分辨率 + 缩放 + 数量）/ 构建 commit
步骤：1) ... 2) ... 3) ...
原始数据：耗时打点（P50/P95/max）、截图或录屏、日志片段（脱敏）
结果：是否达到验收阈值；未达标项的具体数值
处置：达标 → 记录到实施架构「实现边界」；未达标 → 调整方案（选型/降采样/降级）并重验
遗留：后续跟进项与负责人
```

## 5 维护说明

- 新增待验证能力时先加一行任务（编号顺延），再在实现前跑通；
- 结论变更（DONE → FAILED）必须回写本表并在 `CHANGELOG.md` 说明影响；
- 本表阈值与报告 §2.3/§7.2 保持一致，修改阈值需同步更新 README「验收与性能目标」；
- 每条 DONE/FAILED/BLOCKED 必须在 `docs/spikes/` 有对应记录并在本表「状态」列链接，原始数据放 `.verify/spikes/<编号>/`（gitignored）；
- P0 条目 FAILED/BLOCKED 时，先完成技术方案决策（选型/口径/阈值）再重新 spike，不得跳过门禁进入 MVP。
